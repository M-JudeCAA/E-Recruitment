# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

UCAA e-Recruitment System: React (frontend) + Node.js/Express (API) + MySQL via Prisma. Two independent npm projects, `backend/` and `frontend/`, no monorepo tooling. (A root `package.json` exists but only declares `playwright-core` — nothing in the repo uses it; ignore it, run everything from `backend/` or `frontend/`.)

## Commands

### Backend (`backend/`)

```bash
npm install
npm run dev              # API (nodemon, http://localhost:4000) + scheduler worker in one terminal, via scripts/dev.js
npm run dev:api          # API alone (nodemon)
# predev/prestart/prejobs hooks run scripts/prismaGenerate.js (`prisma generate`, tolerating the Windows engine-DLL lock when a client already exists)
npm start                # plain node, no watch
npm test                 # jest, all suites, mocked Prisma client (no DB needed)
npm run test:e2e         # end-to-end suite against a real MySQL DB - needs DATABASE_URL_TEST (a DB whose name contains "test"); see tests-e2e/README.md
npm run jobs             # scheduler worker: runs the maintenance jobs hourly, in its own process (not the API)
npx jest tests/workflowService.test.js   # single suite
npx jest -t "blocks an internal candidate"  # single test by name
npx prisma generate      # regenerate Prisma client after schema.prisma changes
npx prisma migrate dev   # create + apply a new migration locally
npx prisma migrate deploy  # apply pending migrations (what CI/prod uses)
npx prisma migrate status  # check if schema is up to date
npm run seed              # dev only: upsert demo staff accounts with a password (refused in production)
node scripts/createSystemAdmin.js --email x@caa.co.ug --name "..." [--break-glass]  # production: the first system administrator
```

Staff have no passwords in real use - they sign in with Microsoft (see Auth below). The dev seed's demo accounts (password for all: `ChangeMe123!`, at `/staff/login?password`, only while `DEV_PASSWORD_LOGIN=true` and `NODE_ENV` isn't production): `hro@`, `shro@`, `phro@`, `manager@`, `dhra@caa.co.ug` (the five HR roles) and `admin@caa.co.ug` (system administrator, no HR role). The e2e suite signs in the same way.

`backend/.env` is gitignored; required vars are documented in [SETUP.md](SETUP.md) (`DATABASE_URL`, `JWT_SECRET`, `JWT_EXPIRES_IN`, `INTERNAL_EMAIL_DOMAIN`, `ENTRA_TENANT_ID`/`ENTRA_STAFF_CLIENT_ID`/`ENTRA_CANDIDATE_CLIENT_ID`, `PORT`, `FRONTEND_URL`, `SMTP_*`, `UPLOAD_DIR`; optional `DEV_PASSWORD_LOGIN`, `BREAK_GLASS_LOGIN`). The frontend reads `VITE_ENTRA_TENANT_ID`/`VITE_ENTRA_STAFF_CLIENT_ID`/`VITE_ENTRA_CANDIDATE_CLIENT_ID` at build time. SMTP misconfiguration fails silently (`sendMail` logs and returns `null`) rather than crashing request handling — expect emails to silently not arrive if SMTP env vars are wrong.

Scripts live in `backend/scripts/` (`node scripts/<name>.js`). Ten are maintenance jobs, run hourly by the scheduler worker (`scripts/scheduler.js`, `npm run jobs`) or individually from cron (`checkSlaEscalations.js`, `checkVacancyDeadlines.js`, `sendInterviewReminders.js`, `expireOffers.js`, `cleanupPendingRegistrations.js`, `cleanupVerificationTokens.js`, `cleanupRequisitionUploads.js` - removes `requisition-*` uploads (documents and signed copies) no vacancy or draft refers to, after 24 hours; `purgeAccessLog.js` - deletes `DataAccessLog` rows older than the `accessLogRetentionDays` setting, else `ACCESS_LOG_RETENTION_DAYS`, default 730, refusing a setting under 90; `purgeCandidateData.js` - erases candidates inactive for `candidateRetentionMonths`, see Data retention below; `retryHrisHandoffs.js` - re-sends onboarding cases to the HRIS, see Mark as Hired below). Each exports `run()` and records every run in `SystemHealth` via `utils/jobRunner.js` - keep that shape when adding a job, and add it to `JOBS` in `scheduler.js` and in `services/systemHealthService.js`. Scheduled work deliberately never runs on a timer inside the API process. The rest are one-off: `createSystemAdmin.js` (creates/promotes a system administrator, optionally with a break-glass password), `seedDepartments.js`, `seedSlaPolicies.js`, `migrateEducationLevels.js`, plus two demo-data seeders, `seedPreShortlistDemoData.js` and `seedFullWorkflowDemoData.js`, for populating a dev DB at a given workflow stage. `resetDemoData.js` empties a database for a fresh start (only `--yes` acts; without it, it says what it would delete): every table except `StaffUser` and `SlaPolicy` - add any new table to its `TABLES` list - plus the uploads in `UPLOAD_DIR` (app-named files only), then re-seeds the directorates/departments (no positions). `--remove-demo-staff` also deletes the `prisma/seed.js` accounts (`scripts/lib/demoStaff.js`), and refuses unless another active system administrator exists (`createSystemAdmin.js`). The server admin's step-by-step runbook is [docs/database-reset.md](docs/database-reset.md) - keep it in step with the script.

`.github/workflows/ci.yml` runs on push/PR to `main`/`develop`: backend job does `npm install && npx prisma generate && npm test`; backend-e2e job runs `npm run test:e2e` against a MySQL 8 service container; frontend job does `npm install && npm run build`. All must pass.

## Architecture

### MVC-ish split, backend and frontend use matching vocabulary

- **Backend** (`backend/src/`): classic MVC — `routes/` (thin URL→controller wiring only) → `controllers/` (request handling) → `models/` (data access, one file per entity, wraps Prisma) → `config/db.js` (the single shared `PrismaClient` instance, imported everywhere as `prisma`).
- **Frontend** (`frontend/src/`): `views/` (page-level screens, one per route, registered in `App.jsx`) use `components/` (reusable UI: `Navbar`, `Button`, `TextField`, `TextArea`, `Select`, `Card`, `StatusBadge`, `Alert`, `PageHeader`, `Modal`, `ProtectedRoute`) and read/write through `models/` (`apiClient.js` for candidate-facing calls, `staffApiClient.js` for HR-facing calls, `AuthContext.jsx` for session state). "Models" here means the data/state layer, not a UI component.
- **`services/` on the backend** is a layer between controllers and models for business logic that spans multiple models — not classic MVC, but load-bearing here: `workflowService.js` (verification gate, self-approval block, vacancy status computation, offer-decline cascade, qualification snapshots, posting-type transition audit), `meritListService.js` (the post-interview merit list: eligibility, Primary/Reserve assignment, propose/approve), `offerService.js` (offer terms, the offer lifecycle, the candidate-facing offer view), `interviewSchedulingService.js` (slot planning, clash detection, application status after a round is cancelled/no-show), `interviewInvitationService.js` (calendar invitations for panelists and candidates, candidate interview wording), `screeningService.js` (automated applicant screening against vacancy criteria), `tokenService.js` (verification/reset token issuance), `notificationService.js` (in-app/email notification dispatch), `auditService.js` (the audit trail, below), `exportService.js` (the HR CSV exports).

### Request handling & realtime

- **App vs. server**: `src/app.js` builds the Express app (routes, middleware, error handler) and exports it without listening, so the e2e tests can drive it; `src/server.js` loads `.env`, installs the process-level handlers, listens, attaches the WebSocket server, and checks SMTP at start-up.
- **Async errors**: `app.js` loads `express-async-errors` (so a rejected async handler reaches the error middleware as a 500) and `server.js` installs process-level `unhandledRejection`/`uncaughtException` handlers that log and keep the server alive. `utils/asyncHandler.js` is the older explicit per-route wrapper (used in `routes/candidates.js`); both patterns are live, don't assume one or the other.
- **Dashboard push channel**: `realtime/dashboardSocket.js` attaches a `ws` WebSocket server (`/ws/dashboard`) to the same HTTP server. It carries *signals, not data* — `broadcastDashboardEvent(event, payload)` tells connected HR dashboards to re-run their own REST fetch (`dashboardController`/`analyticsController` remain the source of truth). Auth is a first-message `{type:'auth', token}` handshake (staff JWTs only), deliberately **not** a `?token=` query param — see the file-access rule below. Frontend counterpart: `useDashboardEvents` in `frontend/src/models/dashboardSocket.js`, which degrades silently if the socket can't connect.
- **CV autofill** (`POST /api/candidates/me/parse-cv`, `cvParser.js` + `cvHeuristics.js` using `pdf-parse`/`mammoth`): parses an uploaded CV into suggested profile fields via `uploadMemory` and persists nothing. It's unrelated to the application-level CV upload in `applicationDraftController.js`, which does store the file.

### Auth & RBAC

**Sign-in is Microsoft Entra ID for staff and internal candidates** (`services/entraAuthService.js`; frontend `models/entraAuth.js`, MSAL popup, redirect page `public/entra-redirect.html`). Two app registrations: staff (`ENTRA_STAFF_CLIENT_ID`, may be assignment-restricted in Entra) and candidate (`ENTRA_CANDIDATE_CLIENT_ID`, whole tenant). The browser posts the ID token to `POST /api/staff/auth/entra` or `POST /api/candidates/auth/entra`; the API checks signature (JWKS), audience, tenant, age (10 min), not a guest (`acct`), and an `INTERNAL_EMAIL_DOMAIN` address, then issues our own JWT. **Entra proves identity only - it has no HR classification, so access comes from our rows**: staff sign-in needs an active `StaffUser` for that email (linked to the Entra `oid` on first sign-in, `StaffUser.entraObjectId`, oid-only after that; a mailbox now on a different oid is refused). Internal candidates are exactly the Microsoft sign-ins on the candidate app (first sign-in creates the `Internal` `Candidate`, no password, `Candidate.entraObjectId`); a UCAA address can't register a password account (400 `USE_MICROSOFT`), and every password account is External. External candidates keep email + password. Staff have no passwords: `POST /api/staff/auth/login` answers 404 unless `BREAK_GLASS_LOGIN=true` (system administrators with a password from `scripts/createSystemAdmin.js --break-glass`) or `DEV_PASSWORD_LOGIN=true` outside production (seeded demo accounts); each use is audited (`PasswordSignIn`). There is no staff forgot/reset password any more. **An ended session ends in the browser too**: a 401 on any request that carried a session token (outside `/auth/` sign-in calls, which use 401 for wrong credentials) fires `SESSION_ENDED_EVENT` in `apiClient.js`; `AuthContext` signs that session out and the sign-in page says why (`useSessionEndedMessage`: deactivated, or expired) - so deactivating a staff member also takes them out of any open page at once.

**One person, two accounts**: a UCAA employee can have a `StaffUser` and an Internal `Candidate`, matched by `entraObjectId` or email; the session type (`staff`/`candidate`) comes from where they signed in. **Conflict of interest** (`services/conflictOfInterestService.js`, `middleware/applicantConflict.js`): a staff member with any non-Draft application on a vacancy (withdrawn included) - or whose delegator has one, while acting under the delegation - gets 409 `APPLICANT_CONFLICT` from every staff route on that vacancy (`guardVacancy(vacancyFrom.param|application|offer|interview|panelMember|candidate|auditEntity)` after `requireStaffRole`), `GET /api/vacancies/:id` included, and that vacancy is left out of the cross-vacancy lists (applications queue/count, admin vacancies, interviews list/attention, offers lists, pending merit lists, upcoming interviews). Their work on every other vacancy is unaffected. Submitting an application as a staff member notifies the other Principal_HR_Officers (Managers if none), `StaffApplicantConflict`. **Add the guard to any new staff route that works on a vacancy or its applicants.**

**System administrator** (`StaffUser.isSystemAdmin`, `requireSystemAdmin()`): manages staff accounts (`/api/staff-users` writes: create any role, change role/department/admin/active, unlink the Microsoft id; `StaffAccounts.jsx` at `/hr/staff-accounts`) and nothing else - it sits outside `ROLE_RANK`, and an accounts-only admin has `role` null, so no HR gate passes and `fileController` refuses them. No HR role manages accounts. Nobody edits their own account; the last active admin can't be removed. `requireStaffRole`/`requireSystemAdmin` re-read the account each request (`staffModel.findAuthState`), so deactivation (`StaffUser.active`) and role changes apply at once, not at token expiry; inactive staff also get no notifications and lose delegated authority.

Two independent JWT session types, both verified by the same `authenticate` middleware (`backend/src/middleware/auth.js`), distinguished by `req.user.type`: `'candidate'` and `'staff'`. `requireCandidate` gates candidate-only routes; `requireStaffRole(minRole)` gates staff routes by a **cumulative 5-tier role hierarchy**: `HR_Officer < Senior_HR_Officer < Principal_HR_Officer < Manager < Director` (`ROLE_RANK` in `auth.js` — the README's "3-tier" description predates this and is stale, trust the code).

**Delegation**: a staff member can be granted another's role rank for a bounded time window (`Delegation` model). `requireStaffRole` checks for an active delegation only when the requester's own rank fails the gate (avoids a DB query on every request), and if one is used, logs the specific action to `DelegationUsage` — the audit trail shows exactly when a delegation was actually exercised, not merely when it was active. This is distinct from and coexists with an older, simpler `StaffUser.actingAsId` static field; don't conflate the two.

`optionalAuthenticate` fails open to anonymous on a missing/invalid token — used for public browsing endpoints (e.g. job listings) that behave differently for logged-in candidates without requiring login.

### File access

CVs, cover letters, and recommendation letters are served through the authenticated `/api/files/:filename` route (`fileController.js`), never a public `express.static` mount. Staff can view any file; a candidate can only view files attached to their own applications. Since plain `<a href>` downloads can't set an Authorization header, this route also accepts the JWT as a `?token=` query param, scoped only to file downloads — don't extend that query-param acceptance to other routes.

### Org structure model

`Directorate → Department → Position → Vacancy`, each level created/approved by staff and carrying its own `createdById`/`approvedById` audit trail. `Department` has its own approval workflow (`Pending`/`Approved`/`Rejected`, distinct from `Vacancy.status`). `Position.level` is an integer meaningful only *within* the same department (not a global ladder) - entered and shown as words, Officer 1 / Senior 2 / Principal 3 / Manager 4 / Director 5 (`utils/positionLevels.js`, mirrored in the frontend; the API accepts the word or the number), and a position name is unique per-department, not org-wide, because the same title/department name (e.g. "CWG") legitimately recurs under different directorates — see the `@@unique([name, directorateId])` / `@@unique([name, departmentId])` composite keys in `schema.prisma` before assuming a plain unique constraint. **Batch import** (`services/orgImportService.js`, `orgImportController.js`, `OrgImportCard.jsx` on the Departments screen; HR Officer+): an .xlsx or CSV, one row per position (`Directorate, Department, Position, Level`; template from `GET /api/org-import/template`). `POST /api/org-import/preview` checks every row and changes nothing; `POST /api/org-import` re-reads the file and imports it whole or not at all (422 `IMPORT_HAS_ERRORS` with the rows). It never changes what exists - existing rows are skipped, an existing position at another level is a warning. New directorates need Principal_HR_Officer+ (own role or an active delegation, logged); new departments arrive `Pending` with `importId` (`OrgImport` records each import), and `PATCH /api/departments/imports/:importId/approve` (Principal_HR_Officer+) approves the still-pending ones together, with the same SLA/dashboard follow-through as one by one. Their positions are created at once but `GET /api/positions` lists only positions in approved departments.

### Vacancy → Application → Offer lifecycle

- A `Vacancy` is `Internal` or `External` posting type only (never both — `Open` was removed; see the enum comment in `schema.prisma` and `applicationEligibility.js` for the matching bidirectional account/vacancy check). Posting type can transition later, gated at Manager/Director tier and audited via `AuditLog` plus a role/previous-value snapshot on the `Vacancy` row itself.
- **Vacancies are created only from an uploaded, EXCO-approved requisition** (no requisition entity or workflow in this system - EXCO approves outside it). `POST /api/vacancies/requisition` (HR Officer+, `uploadRequisition`, PDF/.docx only, stored as `requisition-<uuid>`) reads it: `utils/documentText.js` extracts the text and refuses scans (422 `SCANNED_DOCUMENT` - no OCR), `utils/requisitionParser.js` reads the labelled facts and headed sections of the UCAA template with a confidence per field (`high`/`medium`/`low`, plus `missing` and `warnings`), and `services/requisitionService.js` matches department/job title/reports-to to the organogram and returns a `prefill` for the form. Screening (structured minimums and questions) is never pre-filled - HR adds it. Alongside it HR uploads the **signed copy** - the scan of the requisition as EXCO signed it (`POST /api/vacancies/requisition/signed-copy`, `uploadSignedRequisition`, PDF/JPG/PNG, stored as `requisition-signed-<uuid>`, never read): the readable document carries the text, the scan the signatures. `create()` needs `requisitionDocument` + `requisitionSignedCopy` (400 `SIGNED_COPY_REQUIRED`) + `requisitionConfirmed: true` and re-reads the stored file itself (`forCreate`), keeping `requisitionDocumentUrl/Name/Hash`, `requisitionSignedCopyUrl/Name` (its SHA-256 in `requisitionDetails.signedCopy`), `requisitionDetails` (what was read, plus `editedFields` - what HR changed from it) on the Vacancy; vacancies from before have no signed copy. One document opens one vacancy (`requisitionDocumentHash` is unique, 409 `DUPLICATE_REQUISITION`); a readvertisement carries the requisition and its signed copy over without the hash. The requisition's "Desirable" items go to `Vacancy.desirableQualifications` (advert text), distinct from `desirableRequirements` (Qualifying questions). All requisition columns are staff-only (`toPublicVacancy`). `pdf-parse`'s pdf.js misreads Buffers from Node's shared pool - always pass `documentText.standaloneBytes(buffer)`. Tests and seeders build requisitions with `scripts/lib/requisitionDocument.js` (and `scripts/lib/demoVacancy.js` / e2e `createVacancyFromRequisition`). **Job description status** (FR-ATS-018): `requisitionService.jdApproval` reads the requisition's JD status as `approved`/`notApproved`/`unknown` (unknown is not refused). On `notApproved`, `create()` answers 422 `JD_NOT_APPROVED` unless `jdExceptionReason` (10+ characters) is sent, stored in `requisitionDetails.jdException`; `approve` then answers 422 `JD_EXCEPTION_NOT_AUTHORISED` until the approver sends `authoriseJdException: true` (frontend `utils/approveVacancy.js` asks first), which records who authorised it. A readvertisement needs it authorised again. A vacancy has at most 5 screening questions, Qualifying and Disqualifying together (`MAX_SCREENING_QUESTIONS`, `vacancyValidation.screeningQuestionCountError`, mirrored in `ScreeningQuestionsEditor`); an older vacancy above the cap can be edited but not given more.
- **Hiring manager** (`Vacancy.hiringManagerName/Email/EntraId/JobTitle`, staff-only, `services/hiringManagerService.js`): the UCAA employee a vacancy is filled for, chosen on New Listing or the vacancy page (`HiringManagerPicker.jsx`; `hiringManager` on create/update/readvertise, an `INTERNAL_EMAIL_DOMAIN` address, `null` clears; readvertising carries it over). Picked from the Entra directory - in the browser with the HR user's delegated Graph permission (`models/entraAuth.js` `searchStaffDirectory`, User.Read.All then User.ReadBasic.All), else `GET /api/directory/people` (`directoryService.js`, app permission + `ENTRA_DIRECTORY_CLIENT_SECRET`; 501 `DIRECTORY_NOT_CONFIGURED` without), else typed in. No system access: `hiringManagers.notify(vacancy, event, details)` emails them (never throws) when the vacancy is approved (`published`), rejected/closed, its deadline passes (`applicationsClosed`, from `checkVacancyDeadlines`), EXCO's shortlist approval is attached, interviews are booked, the merit list is approved, and an offer is accepted or not taken up (declined, withdrawn after issue, expired).
- **Vacancy drafts** (`VacancyDraft`, `vacancyDraftController.js`, `/api/vacancy-drafts`, HR Officer+, private to their writer): the New Listing form plus the requisition read result and the signed copy (`signedCopy`/`signedCopyFilename`), saved with "Save draft" and auto-saved ~2s after changes once a requisition is read (`models/useVacancyDraft.js`); reopened via `/hr/vacancies/new?draft=<id>` from the Vacancies page (`VacancyDraftsList.jsx`). Not a `Vacancy` row - no job reference, never listed. Saves send `baseUpdatedAt` and answer 409 `DRAFT_CHANGED` if another window saved since, rather than overwriting. The EXCO confirmation is never saved; `create()` with `draftId` deletes the draft.
- **Job references** are `UCAA/ADV/{INT|EXT}/{NNN}/{YYYY}` (`utils/jobRefGenerator.js`): a running number per posting type per year (APP_TIMEZONE), taken from the `JobRefSequence` row under its lock inside the transaction that creates the vacancy (`vacancyModel.createWithJobRef`), so numbers are never reused or skipped. Refs made before this (`UCAA/ADV/EXT/09/2026[-n]`) are left as they were.
- **Vacancy approval answers**: approve (`Open`), `PATCH /:id/return` (`Returned`, comment in `returnReason`; HR edits and `PATCH /:id/resubmit`s it, which sets `approvalRequestedAt` and restarts the SLA clock) or `PATCH /:id/reject` (`Rejected`, final, `rejectionReason`); return/reject are Manager+ and need a comment, and the creator is notified (`VacancyReturned`/`VacancyRejected`). Closing (the "unpublish") needs a reason (`closeReason`), as does moving the deadline of a published vacancy (compared by calendar day). Approve/return/reject/close write through `vacancyModel.updateIfStatus`, so two approvers can't both act (409).
- `Vacancy.title`, `Application`'s qualification snapshots, and `Vacancy.approvedByRole`/`postingTypeChangedByRole` are all deliberately denormalized snapshots of what was true at the time an action occurred (not live joins) — if you're tempted to "clean up" one of these into a read-through relation, don't; it's an intentional audit-trail pattern used consistently across this schema.
- **Selection is three steps, each with its own propose/approve split**, shown as stage tabs in the single-vacancy view of `ApplicationManagement.jsx` (`?vacancyId=&stage=shortlist|interviews|merit`): (1) the **interview shortlist** (`ShortlistPipelineBoard`) decides only *who is interviewed, in what order* - it no longer assigns `Primary`/`Reserve` (`listStatus` is written `null`); (2) **interviews** (`VacancyInterviewsPanel`, the Interview Hub); (3) the post-interview **merit list** (`meritListService.js`, `meritListController.js`, `MeritListBoard.jsx`; `Application.meritRank`/`meritListStatus`/`meritStatus`), which ranks `Interviewed` candidates whose latest held round has recorded results with a `Shortlist` or `Hold` verdict. The first `positionsRequired` `Shortlist` candidates are `Primary`, everyone else `Reserve`; a `Hold` may never be Primary nor sit above a `Shortlist`. Proposed by Senior_HR_Officer+ (notifies Principal_HR_Officers, `MeritListProposed`), approved by Principal_HR_Officer+ who proposed none of it; re-proposing needs fresh approval; the list locks (409) once any offer on the vacancy is `Recommended`/`Approved`/`Extended`/`Accepted`. A candidate on the merit list can't be scheduled another round, and a rejection clears their merit entry.
- **Shortlisting committee** (`ShortlistExercise`/`ShortlistMember`/`ShortlistAssignment`/`ShortlistRating`/`ShortlistDecision`; rules in `shortlistCommitteeService.js`, HR side `shortlistCommitteeController.js` + `ShortlistCommittee.jsx` at `/api/shortlist-committee/vacancies/:vacancyId`, members' side `shortlistPanelController.js` + `ShortlistPanelAccess.jsx` at the public `/api/shortlist-panel/:token` and `/shortlist-panel/:token`). Stages `Setup -> Rating -> Moderation -> Closed`. HR (Senior_HR_Officer+) builds the assessment sheet (generated from the vacancy's person specification via `defaultCriteria`, editable, frozen when rating opens) and invites the committee: anyone at UCAA, HR included (an `INTERNAL_EMAIL_DOMAIN` address); someone from outside only as a rare special case with a reason (`ShortlistMember.externalReason`, 422 `EXTERNAL_REASON_REQUIRED` without one, audited); never an applicant for the vacancy; at least 3, one chair (changeable until close). **The DHRA approves the committee** (FR-ATS-046, `ShortlistExercise.nominationStatus` `Draft -> Submitted -> Approved | Returned`): HR `POST .../nomination/submit`s it (Directors notified, `CommitteeNominationSubmitted`); while `Submitted` only a Director (own role or delegation) can change the members, each change audited as `DHRA ...`; a Director other than the submitter `nomination/approve`s it or `nomination/return`s it with a reason (10+ characters; the submitter is told, `CommitteeNominationDecided`); Directors see the queue in the Approvals Center (`GET /api/shortlist-committee/nominations/pending`). `open` answers 422 `NOMINATION_NOT_APPROVED` until approved, and an HR change to the members after approval puts it back to `Draft`. Members' links stop working at `accessExpiresAt` (optional, FR-ATS-048) as well as at close. Rating opens only after the application deadline; every `UnderReview` applicant is assigned (`planAssignments`: a calibration set everyone rates, then sub-panels of `ratersPerApplicant` with balanced load). Members rate through their private link, blind to each other - essential criteria Met(2)/Partly(1)/Not met(0, needs a comment), desirable 1-5 - editable until they submit; they can stand down per applicant, and see that applicant's documents only through the link (`/files/:filename`, checked against their assignments). Only submitted, non-conflicted ratings count, and an applicant with fewer than two of them (`MIN_RATERS`) has every essential criterion go to the chair; during rating GET's `coverage` lists such applicants and HR adds a rater (`/assignments`, emailed; only members who haven't submitted). `computeResults` bands each applicant (Unanimous > Majority > Disputed > NotQualified, by majority of "Met"/"Not met" votes per essential criterion; anything else is Disputed) and ranks by band, weighted consensus score, agreement, then experience; ties share a rank. At moderation the chair rules on disputed items (`ShortlistDecision`, reason required); for an applicant the chair stood down from, HR names an acting chair (`ShortlistExercise.actingChairs`, `PUT /acting-chairs`, never the chair or anyone who stood down from that applicant, emailed) who rules on that applicant in the chair's place; the exercise can't close while any remain. Closing snapshots `committeeRank`/`committeeBand`/`committeeScore`/`committeeAgreement` on each application (stripped from the candidate's own view). HR then proposes N for interview (`/propose`): strictly the top N qualified plus anyone tied at the cut line, at least `positionsRequired` - it lands at `ShortlistProposed` for Principal_HR_Officer approval as before. **EXCO approves the interview shortlist outside the system** (`excoShortlistController.js`, `ExcoShortlistPanel.jsx` on the Interviews step): after the Principal_HR_Officer approval HR prints the shortlist (`GET /api/vacancies/:id/exco-shortlist`, HR Officer+, and `utils/printDocument.js`), EXCO signs it, and a Senior_HR_Officer+ attaches the signed copy (`POST` same path, multipart `document` + optional `excoReference`/`approvedOn` + `struckOff` = JSON application ids EXCO did not approve). That creates an `ExcoShortlistApproval`, sets `Application.excoApprovalId` on everyone it covers (in one transaction, only if they're still `Shortlisted`, unapproved and never interviewed; else 409) and rejects the struck-off ('Not approved for interview by EXCO.'). **Candidates are told they're shortlisted only then** (`approveShortlist` no longer notifies), the struck-off get `ApplicationRejected`. A first interview needs it: `schedule`/`plan`/`sessions` answer 409 `EXCO_APPROVAL_REQUIRED` for an application with no `excoApprovalId` and no interview round yet (later rounds, and rounds booked before this step existed, don't). A later, additional shortlist gets its own approval. **HR cannot reorder**: a vacancy with an exercise refuses `saveRanking` and single `shortlist` (409), and the board hides hand-ranking.
- The interview-shortlist drag-to-rank UI **re-runs `workflowService.assertCanShortlist` for every application in the list before committing the rank** — an internal candidate who isn't `HR_Verified` (with evidence: `Comments` or `ManagerRecommendationLetter`) blocks the whole shortlist commit, regardless of department or posting type.
- **Interviews are scheduled in the system and scored outside it.** The panel scores on paper; afterwards an HR Officer+ records the results from the panel's signed score sheet: `PATCH /api/interviews/:id/results` (multipart, `uploadSupportingDocument.single('scoreSheet')`, `interviewController.recordResults`) with the overall `score` (0-100, one decimal), the verdict `recommendation` (`Shortlist`/`Hold`/`Reject`), optional `notes` (`InterviewRound.resultNotes`) and the sheet (`scoreSheetUrl`/`scoreSheetName`, served through `/api/files`, staff only, opening it is access-logged). The first entry needs the interview time to have passed, the round `Scheduled`, the application still at a `FINALIZABLE_STATUSES` status and the sheet; it moves the round to `Completed` and the application to `Interviewed` - or, on `Reject`, rejects it (`CLEARED_MERIT`) and tells the candidate. Recording again is a correction (`updateIfCompleted`; the sheet optional, replacing the old one if sent): never to or from `Reject` (a rejection is final), and not once the candidate has a `meritStatus` or an offer. Both write `AuditLog` (before/after) on the round and the application; `conductedById`/`resultsRecordedAt` say who recorded it last. There is no separate approval of results - the merit list's propose/approve is the check. There are no per-panelist scores, rubrics, scoring links or interview sessions any more (migration `20261008090000_interview_results_offline` dropped `PanelDayLink`, `InterviewDay`, `PanelAccessToken` and the per-panelist score columns; round scores and verdicts were kept). `PanelMember` is just name, trade, optional email, optional `staffUserId`, `isChair` - no system account needed. `scripts/sendInterviewReminders.js` reminds whoever scheduled an interview (else the vacancy's creator) once (`resultsReminderSentAt`, reset on reschedule), a day after it, that its results aren't recorded (`InterviewResultsOverdue`, grouped per recipient).
- **Calendar invitations** (`interviewInvitationService.js`, `utils/icsCalendar.js`, sent with nodemailer's `icalEvent` so mail clients show Accept/Decline): the candidate gets a `REQUEST` per round in the same email as the notification (UID `interview-<id>@ucaa-erecruitment`, `SEQUENCE` = `rescheduleCount`), a `CANCEL` when it is cancelled. Each panelist with an email gets ONE meeting per vacancy per interview day (APP_TIMEZONE) covering all their non-cancelled rounds that day (`syncPanelInvitations`, UID from the vacancy, day and a hash of the email, `SEQUENCE` from the clock so later updates always win), re-sent whenever a booking, reschedule, cancellation, detail change or panel change touches that day, and turned into a `CANCEL` when nothing is left for them. `ORGANIZER` is `INTERVIEW_ORGANIZER_EMAIL`, else the address in `SMTP_FROM` - replies go there. No Outlook/Graph calendar integration yet.
- **Interview scheduling** lives in the Interview Hub (`/hr/interviews`, `InterviewHub.jsx`: agenda, needs-attention buckets incl. "Results to record", per-vacancy scorecards with the score sheet) with shared modals in `components/interviews/` (`InterviewScheduler` wizard, `InterviewRoundPanel` round workspace with "Record results"/"Correct results"), also opened from `ApplicationReviewCard`. A round has a start time + `durationMinutes`, mode (`In-person`/`Virtual`/`Phone`), venue/link, candidate instructions, staff-only `internalNotes`, and `status` (`Scheduled`/`Completed`/`Cancelled`/`NoShow`; `Completed` is set by recording results). Scheduling is Senior_HR_Officer+. Bulk sessions (`POST /api/interviews/vacancies/:id/plan` dry run, `/sessions` to book) lay candidates out back to back in one transaction (`interviewModel.createSession`, conditional on each application still being schedulable) under a shared `sessionKey`. Every booking/reschedule/panel add is checked for candidate, panelist and room clashes and answers 409 `SCHEDULE_CONFLICT` unless `allowConflicts` is sent. Cancel/no-show move an `InterviewScheduled` application back (`statusAfterRoundClosed`); cancelled/no-show rounds are skipped by `recommendOffer`. Candidates confirm or ask for another time (`candidateResponse`, reset on every reschedule) and download .ics files; anything handing an `InterviewRound` to a candidate must go through `utils/candidateInterview.js` `toCandidateInterview` (score, verdict, notes and score sheet stay staff-only). Times in messages use `APP_TIMEZONE` (default `Africa/Kampala`).
- **Offers** (`offerService.js`, `offerController.js`; frontend `components/offers/`) are step four, fed by the merit list. Lifecycle: `Recommended` → `Approved` (issued) | `Returned` (approver sent it back with `returnReason`; PHRO revises via `PATCH /api/applications/offers/:offerId`, which resubmits it and makes the reviser the recommender for the self-approval check) → `Accepted` | `Declined` (optional `declineReason`) | `Expired` | `Withdrawn`. `Extended` is legacy, never written. `recommend-offer` (Principal_HR_Officer+) requires the terms in the body (`offerService.parseTerms`: salary, employment category (+ `contractMonths` for contracts), start date, optional allowances/duty station/`conditions`, `responseDays` 3-30) and `offerService.recommendBlocker` to pass: application at `Interviewed`, latest held round recorded `Shortlist` or `Hold` (a later `Reject` wins), **and** `meritStatus === 'Approved' && meritListStatus === 'Primary'` (a `Hold` only gets there by promotion); it snapshots `meritRankAtOffer`/`interviewScoreAtOffer`. `GET /api/applications/:id/offer-draft` prefills the form. Approval (Manager+, never the recommender) refuses offers with no terms (pre-redesign rows) or on a filled vacancy, and fixes `responseDeadline = approval + responseDays`; `scripts/expireOffers.js` reminds the candidate two days before (`OfferExpiring`, guard `responseReminderSentAt`) and expires lapsed offers; accept/decline after the deadline answer 409 even before the job runs. **Declined, Expired and Withdrawn all go through `workflowService.closeOffer`**, which promotes the next `Reserve` on the approved merit list (by `meritRank`; vacancies with no merit list fall back to the old `rank`/`listStatus`) to `Primary` unless the vacancy is already filled, and recomputes `Vacancy.status` (`Open`/`PartiallyFilled`/`Filled` from accepted-offer count vs. `positionsRequired`) — status computation, not a stored transition; Principal_HR_Officers are told who moved up (`OfferDeclined`/`OfferExpired`; a withdrawal returns `promotedApplicationId` instead). When an acceptance fills a vacancy, or is refused because it is already full, Principal_HR_Officers are told about offers still `Recommended`/`Returned`/`Approved` on it (`VacancyFilledWithOpenOffers`). Withdraw (Principal_HR_Officer+, any open offer) records `withdrawnById`/`withdrawalReason`, audits in `AuditLog`, and notifies the candidate (`OfferWithdrawn`) only if the offer had been issued. The application stays `Offered` with its one Offer row (`applicationId` is unique). **Candidates never see an offer before it is issued**: `candidateController.myApplications` passes it through `offerService.toCandidateOffer` (null until `approvedDate`, terms only), shows an `Offered` application with no visible offer as `Interviewed`, and strips `rank`/`listStatus`/merit fields. `GET /api/applications/offers` is the cross-vacancy tracker (HR dashboard Offers tab, `OfferTracker.jsx`).
- **Document templates** (`config/documentTemplates.js` defaults, `DocumentTemplate` rows for HR's edits, `services/templateService.js`, `services/documentService.js`, `documentController.js` at `/api/documents`; frontend `DocumentTemplates.jsx` at `/hr/templates`): the offer letter, appointing instrument (only once `Accepted`), interview invitation letter, regret letter (only `Rejected`) and the interview shortlist for EXCO - UCAA's own default wording until official templates arrive. Bodies are HTML with `{{placeholder}}`s (escaped; `block` placeholders like `{{conditionsList}}`/`{{shortlistTable}}` are server-built markup); only the placeholders listed per template are filled, an empty value prints blank, and saving one that uses an unknown placeholder answers 400 `UNKNOWN_PLACEHOLDERS`. Anyone in HR reads/previews (`POST /templates/:key/preview`, sample values); Manager+ saves (`PUT`, sanitised like job adverts, audited as `DocumentTemplate`) or resets (`DELETE`). Documents come back as `{ title, html }` (`GET /api/documents/offers/:offerId/offer-letter|appointment`, `/interviews/:id/invitation`, `/applications/:id/regret-letter`, `/vacancies/:id/exco-shortlist`, all `guardVacancy`ed and access-logged) and the browser prints them (`utils/printDocument.js` `printFromApi`, "Save as PDF"). The candidate gets their issued offer's letter at `GET /api/candidates/me/offers/:offerId/letter`. **`Offer.viewedAt`** is set the first time the candidate sees the issued offer (My Applications or the letter) - shown in the offer trail (FR-ATS-065).
- **Mark as Hired** (FR-ATS-067 to 069, BR-ATS-11; `services/hireService.js`, `hireController.js`, `components/offers/HireSection.jsx` inside `OfferActions`): on an `Accepted` offer a Principal_HR_Officer+ `POST /api/applications/offers/:offerId/hire` with the signed appointing instrument (multipart `signedInstrument`, `uploadSignedAppointment`, stored `appointment-signed-<uuid>`; 400 `SIGNED_INSTRUMENT_REQUIRED`). It opens one `Hire` - the onboarding case, `caseRef` `UCAA/ONB/NNN/YYYY` from the `JobRefSequence` row `ONB` in the same transaction; `applicationId`/`offerId` unique, so a repeat answers 200 `alreadyHired` with the same case - with `package` (person, education, experience, certificates, job, terms, documents with SHA-256), adds one to the position's `occupied` (where a headcount is kept) and emails the hiring manager (`hired`). The application stays `Offered`; the Hire row is what says hired. `services/hrisHandoffService.js` POSTs the package to `HRIS_HANDOFF_URL` (`Idempotency-Key: caseRef`, optional `HRIS_HANDOFF_TOKEN`), storing `onboardingCaseId` from the answer; failures stay `Pending` and are retried by `scripts/retryHrisHandoffs.js` with growing waits, `Failed` after `MAX_ATTEMPTS` (Directors alerted, `SystemHealthAlert`); HR can `.../hire/retry`. Without the URL a case is `NotConfigured` and HR downloads `.../hire/package`. `GET /api/applications/hires` lists cases.
- **Approved headcount** (FR-ATS-006, `services/headcountService.js`): `Position.headcount` (approved posts, null = not recorded, nothing checked) and `occupied`, set at `PUT /api/positions/:id/headcount` (Principal_HR_Officer+, audited) on the Departments screen (`PositionHeadcountCard.jsx`); `GET .../headcount` gives `available` = headcount - occupied - posts still being recruited for by other `PendingApproval`/`Returned`/`Open`/`PartiallyFilled` vacancies (less their hires). Create/readvertise/raising `positionsRequired` beyond it answers 422 `HEADCOUNT_EXCEEDED` (with `headcount`) unless `headcountExceptionReason` (10+ characters), kept in `requisitionDetails.headcountException`; approving such a vacancy needs a Director (own role or delegation; 403 `HEADCOUNT_EXCEPTION_NEEDS_DIRECTOR`) who sends `authoriseHeadcountException: true` (`utils/approveVacancy.js` asks). On a published vacancy only a Director can raise it, authorising it at once. No budget check - there is no budget data.
- **Audit trail** (`services/auditService.js`): `audit.record({ entityType, entityId, action, actor: audit.actorFrom(req), before, after, fields, comment, details })` writes `AuditLog` with the changed values (`payload.changes`), the comment and the delegation in use (`actingAsId`); a candidate's own action is marked `payload.actor`. It runs after the action committed and never throws. Vacancy, application, offer and merit-list actions all record here; `GET /api/audit/:entityType/:entityId` (HR Officer+, Vacancy/Application/Offer/InterviewRound) returns only `changes`/`comment`, never the rest of the payload, and `AuditTrail.jsx` shows it. Use it for any new state change.
- **Access log** (FR-ATS-081, `services/accessLogService.js`, `DataAccessLog`): the read side - who *viewed* candidate data. `accessLog.record(req, { action, vacancyId, applicationId, candidateIds, detail, committeeMember })` is called where staff see applicants (`vacancyController.listApplications`, `applicationController.list`), open a document (`fileController`, staff only), export a report (`exportController`, with the report's `candidateIds`), and where shortlisting committee members view an applicant or document (recorded by name/email, `actorType: 'committee'`). Identical repeats are recorded once per 10 minutes (in-memory throttle, per process) and it never throws. `GET /api/audit/access/applications/:applicationId` (Manager+) lists views of the application and of anything whose `candidateIds` included its candidate (`array_contains` on the JSON column); `AccessLog.jsx` shows it on `ApplicationReviewCard`. Rows are kept `ACCESS_LOG_RETENTION_DAYS` (default 730) and then deleted by `scripts/purgeAccessLog.js`.
- **Data retention and erasure** (FR-ATS-079/080): `services/settingsService.js` holds settings (`Setting` rows, defaults and limits in `DEFINITIONS`: `candidateRetentionMonths` 24 (6-120), `accessLogRetentionDays`), changed at `GET/PUT /api/settings[/:key]` by a system administrator or Manager+ (`requireSystemAdminOrRole`, audited) on `SettingsAndData.jsx` (`/hr/settings`). `services/candidatePurgeService.js` `purgeCandidate` erases a candidate's personal data in one transaction: deletes profile entries, internal profile, tokens, notifications and application documents, clears the candidate-written application fields and the free text about them, anonymises the `Candidate` row (every optional field, name `Removed candidate N`, `purgedAt`) and keeps the rows so the recruitment history still adds up; then deletes the files and writes `DataPurgeLog` (counts, no personal data). Never a hired candidate or one with an application in progress (`blockerFor`). Candidates download everything held about them (`GET /api/candidates/me/data-export`) and ask for erasure (`POST /api/candidates/me/data-requests`, `DataSubjectRequest`, notifies Managers `DataErasureRequested`) from `YourDataCard.jsx` on their profile; a Manager+ completes it (`/api/data-protection/requests/:id/complete`, emails the candidate) or refuses it with a reason (`DataRequestRefused`). `scripts/purgeCandidateData.js` purges everyone inactive for the retention period. When adding a candidate-data column, decide whether the purge must clear it (`APPLICATION_TEXT`/`APPLICATION_JSON`; optional `Candidate` fields are cleared automatically).
- **Duplicate applicants** (FR-ATS-037): `Candidate.phoneKey` is the last 9 digits of the phone (`utils/phoneKey.js`, set when a registration is confirmed), so `0772 123456` and `+256772123456` match. Registering with a phone another account uses answers 409 `POSSIBLE_DUPLICATE_ACCOUNT` (never naming that account) until the person resends with `confirmNotDuplicate: true` (`Register.jsx` asks: sign in, reset password, or "it's not me"). `duplicateApplicantService.annotate` adds `possibleDuplicates` to applicant lists (same vacancy, other candidate, same `phoneKey`), flagged on the board card and `ApplicationReviewCard`. Email and NIN can't repeat at all.
- **CSV exports** (`exportService.js`, `exportController.js`, `utils/csv.js`): `GET /api/vacancies/:id/export/shortlisting-report` and `GET /api/applications/vacancies/:vacancyId/merit-list/export` (HR Officer+), always the whole vacancy; each export is audited on the vacancy. `utils/csv.js` prefixes cells starting with `= + - @` so candidate-typed text can't run as a spreadsheet formula. The frontend downloads them as blobs with the Authorization header (`CsvDownloadButton.jsx`) - not via `?token=`.
- Self-approval is blocked at the service layer: whoever created a vacancy cannot approve it (`assertNotSelfApproval`), whoever proposed a shortlist cannot approve it (`assertNotSelfApprovedShortlist`), and whoever recommended an offer cannot approve it (`assertNotSelfApprovedOffer`).
- Offer acceptance locks the vacancy row (`SELECT ... FOR UPDATE`) as the first statement of its transaction and refuses once accepted offers reach `positionsRequired` — keep the lock first; see the comment on `acceptOfferTransactionally`.
- Candidates and guests only see a vacancy via `GET /api/vacancies/:id` if `listPublic` would list it for them or they already have an application on it (404 otherwise). Any response that hands a vacancy row to a non-staff caller must pass it through `utils/publicVacancy.js` `toPublicVacancy`, which strips HR-only and audit columns.
- `ApplicationStatus.Rejected` is reachable exactly two ways, both recording `rejectedAt`/`rejectedById`/`rejectionReason` and firing an `ApplicationRejected` candidate notification: an explicit HR action (`PATCH /api/applications/:id/reject`, Senior_HR_Officer+, refused once the application is already `Draft`/`Offered`/`Rejected`/`Withdrawn`) or an interview's results recorded with `recommendation === 'Reject'` at `interviewController.recordResults` (routes there instead of to `Interviewed`). Candidates also get notified on shortlisting, an interview being scheduled, submission, and an offer becoming `Approved` — see `candidateNotificationService.notifyCandidate` call sites.

### Candidate application flow

Candidate-facing application is a multi-step wizard (`frontend/src/views/apply-wizard/`: `JobDetailsStep`, `ProfileStep`, `InternalProfileStep`, `QuestionsStep`, `DocumentsStep`, `ReviewStep`, `SubmitStep`), backed by a real draft/submit/withdraw workflow (`applicationDraftController.js`) rather than local-only wizard state — profile fields (`location`, `linkedinUrl`, etc.) persist on `Candidate` across every application; per-application answers (`desiredSalary`, `whyThisRole`, `desirableResponses`, etc.) persist on `Application`. `Vacancy.desirableRequirements` ("Qualifying" questions in the HR editor) are Yes/No or number questions with a stable generated `id` per requirement so an applicant's snapshotted answer stays attributable even if the vacancy wording is later edited; a "No" answer is informational only (a ranking signal, never a block).

**Screening happens at the point of application**: `submit()` runs `screeningService.assessEligibility` and refuses (422 `NOT_ELIGIBLE` with `reasons`) a candidate who fails any structured minimum on the vacancy (education, experience, age, flying hours, exam grades, CGPA - missing profile data counts as a fail) or answered a `disqualifyingRequirements` question the wrong way (400 while one is unanswered). Only eligible candidates reach the applicant pool, and every submitted application is stored already screened; Begin Review re-screens against the current profile. The wizard surfaces the same check early via `GET /api/applications/eligibility/:vacancyId` (Job Details warning, Submit step) and stops the candidate on the Questions step as soon as a Disqualifying answer fails (`utils/screeningQuestions.js`). Submit also requires explicit consent (`{ consent: true }`, else 400 `CONSENT_REQUIRED`), stored as `consentGivenAt`/`consentNoticeVersion` against the privacy notice at `/privacy` (`frontend/src/data/privacyNotice.js`; bump its version together with `backend/src/config/privacyNotice.js` - the wording is a draft pending UCAA Legal). The Uganda NIN (`Candidate.nationalId`) is the only identity document a candidate gives - no passports, no ID-type choice (`idType` was dropped): it is stored upper-cased (`normalizeNationalId`) and must match `NATIONAL_ID_RE` at registration, on profile save and for profile completeness. `Candidate.districtOfOrigin` is required for a complete profile; `location` is the place of residence. **Evidence** (`utils/screeningEvidence.js`, mirrored in `frontend/src/utils/screeningEvidence.js`): what screening relies on must be backed by an `Evidence` `ApplicationDocument` filed under its `evidenceKey` - `nationalId` for an age limit, `flyingHours`, `examResults`, `experience` (minimum experience), `transcript` (minimum CGPA), and `question:<id>` for a screening question HR marked `evidenceRequired` (with `evidenceLabel`) that the candidate answered Yes or with a number above 0. Upload with `category: 'Evidence'` + `evidenceKey` (refused if the vacancy doesn't ask for it; labelled with the requirement); submit answers 400 `EVIDENCE_REQUIRED` with `missing` after the eligibility check, and `GET /api/applications/eligibility/:vacancyId` returns `evidence` with `provided`. The Documents step collects them. Submit also requires at least one `Academic` `ApplicationDocument` (plus optional `Other` documents; PDF/Word/JPG/PNG, uploaded one at a time via `POST/DELETE /api/applications/:id/documents` while the application is a Draft, served through `/api/files` like cover letters).

### Frontend routing/layout

`App.jsx` splits routes into two groups: most routes render inside `PaddedLayout` (adds a padding gutter around `Outlet`); a few self-contained full-bleed pages (`/register`, `/login`, `/apply/:vacancyId`, `/staff/login`) are registered as siblings outside that layout because they manage their own edge-to-edge background and would get an unwanted double inset otherwise. Keep that distinction in mind when adding new routes — decide whether the new view needs the padded shell or manages its own full-bleed layout.

`ProtectedRoute.jsx` exports `RequireCandidate` and `RequireStaff` (the latter taking `minRole`, checked against the same `ROLE_RANK` hierarchy as the backend) — client-side gating only; the backend middleware is the real enforcement.

### Theming

Tailwind is present but **`preflight` is disabled** (`tailwind.config.js`) — older pages were built against plain browser defaults plus `theme.css`, so only Tailwind's utility classes apply (used mainly in newer markup like the apply wizard). Don't re-enable preflight; it would restyle every page. Tailwind directives are imported at the top of `theme.css`.

All brand tokens (colors, spacing, radius, font) live in `frontend/src/theme.css` as CSS variables. Every reusable component reads from these variables rather than hardcoding values, and every view uses these components instead of one-off inline styles or browser dialogs (use themed `Modal`, never `window.prompt`/`window.confirm`). `StatusBadge` centralizes color-per-status-enum (vacancy/application/offer/verification status) in one lookup table — add new status colors there, not per-view. To rebrand: edit `theme.css` variables only.

### SLA / notifications

`SlaPolicy` (per `taskType` + role `tier`, duration in hours) and `TaskEscalation` back an SLA-tracking layer for `VacancyApproval`/`DepartmentApproval`/`OfferApproval`, checked via `scripts/checkSlaEscalations.js`. `Notification` supports `InApp`/`Email` channels per recipient staff user, surfaced in the UI via `NotificationBell.jsx`. A separate script, `scripts/checkVacancyDeadlines.js`, notifies a vacancy's creator exactly once (via `Vacancy.deadlineNotifiedAt`) when its application deadline passes while still `Open`/`PartiallyFilled` - it reuses the same `Notification`/`notify()` plumbing (hence the `VacancyDeadlinePassed` `SlaTaskType` value) but is not part of the escalation-tier machinery above. Same for `OfferDeclined` and `VacancyFilledWithOpenOffers` (to Principal_HR_Officers, see the offer lifecycle above) and `SystemHealthAlert` (in-app only, to Directors). `applicationDraftController.submit` fires a `NewApplicationSubmitted` notification (same `notify()` plumbing, also not part of the escalation machinery) to the vacancy's creator on every submission, Internal or External - distinct from and in addition to `workflowService.notifySupervisor`, which only ever fires for Internal candidates and notifies their declared supervisor, not HR.

**Candidate-facing notifications** are a separate, parallel system - `CandidateNotification`/`CandidateNotificationType` (not `Notification`/`SlaTaskType` above), dispatched via `candidateNotificationService.notifyCandidate(candidateId, type, message)` and surfaced via `CandidateNotificationBell.jsx`. A distinct model rather than reusing `Notification`, since `Candidate.id` and `StaffUser.id` are independent autoincrement sequences that can collide in value - see the schema comment on `CandidateNotification`. Current types: `ProfileCompleted` (fired once, `profileCompletionService.js`), `ApplicationSubmitted`, `ApplicationShortlisted`, `InterviewScheduled`, `ApplicationRejected`, `OfferReceived` (fired when an offer reaches `Approved`, the point `CandidateOfferPanel` actually lets the candidate accept/decline it - not at `Recommended`, which they can't see), `OfferWithdrawn`, `OfferExpiring`, `OfferExpired` (both from `scripts/expireOffers.js`), `DataRequestRefused`, `InterviewRescheduled`, `InterviewCancelled`, `InterviewReminder` (the last from `scripts/sendInterviewReminders.js`, about a day ahead). Staff-side interview notices reuse `notify()` with `SlaTaskType` `InterviewRescheduleRequested` and `InterviewResultsOverdue` (`InterviewReadyToFinalize`, `InterviewScoresOverdue` and `InterviewSessionNotStarted` are legacy enum values, no longer sent).

**System health**: `SystemHealth` rows (`job:<name>` per maintenance job, `mail` for outgoing email) record the last success/failure. `utils/mailer.js` writes the `mail` row on every send (successes throttled) and `sendMail` still returns `null` rather than throwing; `SMTP_HOST=json` uses nodemailer's jsonTransport for dev/tests; a missing `SMTP_HOST` counts as a failure. `services/systemHealthService.js` turns the rows into staff warnings for `GET /api/dashboard/system-health` (shown by `SystemHealthBanner.jsx` on the HR home page) and alerts Directors in-app at most once a day per key. Error text stays server-side - never send `lastError` to the browser.

**Rate limiting**: `middleware/rateLimit.js` limits candidate/staff login, forgot-password and candidate registration per address and per account (in-memory, per process). Per-address limits depend on `app.set('trust proxy')`, set from `TRUST_PROXY` (default `loopback`).

## Testing conventions (backend)

Every suite in `backend/tests/` mocks the shared Prisma client via `jest.mock('../src/config/db', () => require('./__mocks__/db'))` — `tests/__mocks__/db.js` is a hand-maintained object of `jest.fn()`s per model/method. **When adding a new Prisma call in application code, add the corresponding mock method to `tests/__mocks__/db.js` first**, or the test will fail with "not a function" rather than a useful assertion failure. Unit tests never touch a real database. `beforeEach(() => jest.clearAllMocks())` is the standard pattern at the top of each suite.

`backend/tests-e2e/` is the exception: the real app against a real MySQL database (`npm run test:e2e`, `DATABASE_URL_TEST`), for what mocks can't show - locking, unique-key races, queries that no longer match the schema. Each test empties the database; use the factories in `tests-e2e/helpers.js`. The default `npm test` ignores this folder.

## Known gaps (intentional, not oversights)

- The migration history can't build a database from scratch (`20260915120000_age_flying_hours_exam_grades` alters a column no earlier migration creates - columns were added directly on the shared DB; see the READMEs in `prisma/migrations/`). The e2e suite uses `prisma db push` instead. New migrations still go in `prisma/migrations/` as usual.
- Rate limits are in-memory per API process; a multi-process deployment would need a shared store.
- No frontend test suite.
- `docker-compose.yml` exists but isn't wired up for local dev — use the two-terminal `npm run dev` flow (backend + frontend) in [SETUP.md](SETUP.md) instead.
- Entra ID is used for sign-in only - no HRMS/Graph sync. `candidateType` Internal means "signed in with a UCAA Microsoft account"; `InternalProfile` fields (supervisor etc.) are self-declared + HR-verified, not read from Entra, which holds no department/trade data. Committee members and interview panelists still get link-only access (no Microsoft sign-in yet).
