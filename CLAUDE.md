# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

UCAA e-Recruitment System: React (frontend) + Node.js/Express (API) + MySQL via Prisma. Two independent npm projects, `backend/` and `frontend/`, no monorepo tooling. (A root `package.json` exists but only declares `playwright-core` — nothing in the repo uses it; ignore it, run everything from `backend/` or `frontend/`.)

## Commands

### Backend (`backend/`)

```bash
npm install
npm run dev              # API (nodemon, http://localhost:4000) + scheduler worker in one terminal, via scripts/dev.js
npm run dev:api          # API alone (nodemon)
# predev/prestart/prejobs hooks run scripts/prismaGenerate.js (`prisma generate`, tolerating the Windows engine-DLL lock when a client already exists)
npm start                # plain node, no watch
npm test                 # jest, all suites, mocked Prisma client (no DB needed)
npm run test:e2e         # end-to-end suite against a real MySQL DB - needs DATABASE_URL_TEST (a DB whose name contains "test"); see tests-e2e/README.md
npm run jobs             # scheduler worker: runs the maintenance jobs hourly, in its own process (not the API)
npx jest tests/workflowService.test.js   # single suite
npx jest -t "blocks an internal candidate"  # single test by name
npx prisma generate      # regenerate Prisma client after schema.prisma changes
npx prisma migrate dev   # create + apply a new migration locally
npx prisma migrate deploy  # apply pending migrations (what CI/prod uses)
npx prisma migrate status  # check if schema is up to date
npm run seed              # dev only: upsert demo staff accounts with a password (refused in production)
node scripts/createSystemAdmin.js --email x@caa.co.ug --name "..." [--break-glass]  # production: the first system administrator
```

Staff have no passwords in real use - they sign in with Microsoft (see Auth below). The dev seed's demo accounts (password for all: `ChangeMe123!`, at `/staff/login?password`, only while `DEV_PASSWORD_LOGIN=true` and `NODE_ENV` isn't production): `hro@`, `shro@`, `phro@`, `manager@`, `dhra@caa.co.ug` (the five HR roles) and `admin@caa.co.ug` (system administrator, no HR role). The e2e suite signs in the same way.

`backend/.env` is gitignored; required vars are documented in [SETUP.md](SETUP.md) (`DATABASE_URL`, `JWT_SECRET`, `JWT_EXPIRES_IN`, `INTERNAL_EMAIL_DOMAIN`, `ENTRA_TENANT_ID`/`ENTRA_STAFF_CLIENT_ID`/`ENTRA_CANDIDATE_CLIENT_ID`, `PORT`, `FRONTEND_URL`, `SMTP_*`, `UPLOAD_DIR`; optional `DEV_PASSWORD_LOGIN`, `BREAK_GLASS_LOGIN`). The frontend reads `VITE_ENTRA_TENANT_ID`/`VITE_ENTRA_STAFF_CLIENT_ID`/`VITE_ENTRA_CANDIDATE_CLIENT_ID` at build time. SMTP misconfiguration fails silently (`sendMail` logs and returns `null`) rather than crashing request handling — expect emails to silently not arrive if SMTP env vars are wrong.

Scripts live in `backend/scripts/` (`node scripts/<name>.js`). Eleven are maintenance jobs, run hourly by the scheduler worker (`scripts/scheduler.js`, `npm run jobs`) or individually from cron (`checkSlaEscalations.js`, `sendApprovalReminders.js` - approval notices for anything waiting that someone was never told about, and the daily reminder, see SLA / notifications below; `checkVacancyDeadlines.js`, `sendInterviewReminders.js`, `expireOffers.js`, `cleanupPendingRegistrations.js`, `cleanupVerificationTokens.js`, `cleanupRequisitionUploads.js` - removes `requisition-*` uploads (documents and signed copies) no vacancy or draft refers to, after 24 hours; `purgeAccessLog.js` - deletes `DataAccessLog` rows older than the `accessLogRetentionDays` setting, else `ACCESS_LOG_RETENTION_DAYS`, default 730, refusing a setting under 90; `purgeCandidateData.js` - erases candidates inactive for `candidateRetentionMonths`, see Data retention below; `retryHrisHandoffs.js` - re-sends onboarding cases to the HRIS, see Mark as Hired below). Each exports `run()` and records every run in `SystemHealth` via `utils/jobRunner.js` - keep that shape when adding a job, and add it to `JOBS` in `scheduler.js` and in `services/systemHealthService.js`. Scheduled work deliberately never runs on a timer inside the API process. The rest are one-off: `applyScreeningSuggestions.js` (gives vacancies still advertised or awaiting approval the screening their Essential Requirements suggest - empty fields only, an existing Qualifying question about the qualification moved to Disqualifying; lists the changes, applies only with `--yes`, audited), `createSystemAdmin.js` (creates/promotes a system administrator, optionally with a break-glass password), `syncStaffGroup.js` (puts active staff accounts in the staff app's Entra group and deactivated ones out, for accounts from before that was managed here; lists, applies with `--yes`), `seedDepartments.js` (UCAA's organisation structure from HR's workbook `scripts/data/ucaa-org-structure.xlsx`, the import's layout: makes the database match it in place - matched by code, earlier codes carried over by `DEPARTMENT_RENAMES`/`POSITION_MOVES` so ids and what uses them survive, the rest created approved, leftovers deleted when unused else listed, Corporate's head set to the DDG; `--dry-run` does it in a rolled-back transaction; `seed()` is exported for `tests-e2e/orgStructureSeed.e2e.test.js`), `seedSlaPolicies.js`, `migrateEducationLevels.js`, plus two demo-data seeders, `seedPreShortlistDemoData.js` and `seedFullWorkflowDemoData.js`, for populating a dev DB at a given workflow stage. `resetDemoData.js` empties a database for a fresh start (only `--yes` acts; without it, it says what it would delete): every table except `StaffUser` and `SlaPolicy` - add any new table to its `TABLES` list - plus the uploads in `UPLOAD_DIR` (app-named files only), then re-seeds the organisation structure (directorates, departments, positions). `--remove-demo-staff` also deletes the `prisma/seed.js` accounts (`scripts/lib/demoStaff.js`), and refuses unless another active system administrator exists (`createSystemAdmin.js`). The server admin's step-by-step runbook is [docs/database-reset.md](docs/database-reset.md) - keep it in step with the script.

### CI

`.github/workflows/ci.yml` runs on push/PR to `main`/`develop`: backend job does `npm install && npx prisma generate && npm test`; backend-e2e job runs `npm run test:e2e` against a MySQL 8 service container; frontend job does `npm install && npm test && npm run build`. All must pass.

**CD**: a push to `main` that passes CI goes live on the test (UAT) server within ~5 minutes - pulled, not pushed: `deploy/lan/auto-deploy.ps1` (scheduled task, SYSTEM) asks GitHub's public API for the newest successful `ci.yml` run on `main` and runs `deploy/lan/update-uat.ps1 -Commit <sha>` (pause app, `npm ci`, `db:prepare`, build to `dist-next` and swap, resume); a failed deploy rolls back to the previous commit. No self-hosted runner (public repo). Merging to `main` is therefore a release to testers - new migrations included. See [deploy/lan/README.md](deploy/lan/README.md).

## Architecture

### MVC-ish split, backend and frontend use matching vocabulary

- **Backend** (`backend/src/`): classic MVC — `routes/` (thin URL→controller wiring only) → `controllers/` (request handling) → `models/` (data access, one file per entity, wraps Prisma) → `config/db.js` (the single shared `PrismaClient` instance, imported everywhere as `prisma`).
- **Frontend** (`frontend/src/`): `views/` (page-level screens, one per route, registered in `App.jsx`) use `components/` (reusable UI: `Navbar`, `Button`, `TextField`, `TextArea`, `Select`, `Card`, `StatusBadge`, `Alert`, `PageHeader`, `Modal`, `ProtectedRoute`) and read/write through `models/` (`apiClient.js` for candidate-facing calls, `staffApiClient.js` for HR-facing calls, `AuthContext.jsx` for session state). "Models" here means the data/state layer, not a UI component.
- **`services/` on the backend** is a layer between controllers and models for business logic that spans multiple models — not classic MVC, but load-bearing here: `workflowService.js` (verification gate, self-approval block, vacancy status computation, offer-decline cascade, qualification snapshots, posting-type transition audit), `meritListService.js` (the post-interview merit list: eligibility, Primary/Reserve assignment, propose/approve), `offerService.js` (offer terms, the offer lifecycle, the candidate-facing offer view), `interviewSchedulingService.js` (slot planning, clash detection, application status after a round is cancelled/no-show), `interviewInvitationService.js` (calendar invitations for panelists and candidates, candidate interview wording), `screeningService.js` (automated applicant screening against vacancy criteria), `tokenService.js` (verification/reset token issuance), `notificationService.js` (in-app/email notification dispatch), `auditService.js` (the audit trail, below), `exportService.js` (the HR CSV exports).

### Request handling & realtime

- **App vs. server**: `src/app.js` builds the Express app (routes, middleware, error handler) and exports it without listening, so the e2e tests can drive it; `src/server.js` loads `.env`, installs the process-level handlers, listens, attaches the WebSocket server, and checks SMTP at start-up.
- **Error codes**: `sendError`/`classifyError` pass an `AppError`'s `code` through to the JSON (`{ error, code }`), so a service can throw a documented code itself.
- **Async errors**: `app.js` loads `express-async-errors` (so a rejected async handler reaches the error middleware as a 500) and `server.js` installs process-level `unhandledRejection`/`uncaughtException` handlers that log and keep the server alive. `utils/asyncHandler.js` is the older explicit per-route wrapper (used in `routes/candidates.js`); both patterns are live, don't assume one or the other.
- **Dashboard push channel**: `realtime/dashboardSocket.js` attaches a `ws` WebSocket server (`/ws/dashboard`) to the same HTTP server. It carries *signals, not data* — `broadcastDashboardEvent(event, payload)` tells connected HR dashboards to re-run their own REST fetch (`dashboardController`/`analyticsController` remain the source of truth). Auth is a first-message `{type:'auth', token}` handshake (staff JWTs only), deliberately **not** a `?token=` query param — see the file-access rule below. Frontend counterpart: `useDashboardEvents` in `frontend/src/models/dashboardSocket.js`, which degrades silently if the socket can't connect. **From the scheduler worker** (another process, so `broadcastDashboardEvent` there reaches nobody): `utils/dashboardSignal.js` `signalDashboards(event, payload)` POSTs `/api/internal/dashboard-events` (`INTERNAL_API_URL`, default `http://127.0.0.1:PORT`), signed with an HMAC of `JWT_SECRET` over a timestamp and the body (60 s; never a bearer token), and the API broadcasts it - `MaintenanceRun` once per scheduler cycle, and after a job run on its own (`runAsScript`). Never throws.
- **CV autofill** (`POST /api/candidates/me/parse-cv`, `cvParser.js` + `cvHeuristics.js` using `pdf-parse`/`mammoth`, built-in rules only - no outside service): parses an uploaded CV into suggested profile fields via `uploadMemory` and persists nothing. `cvParser.extractText` rebuilds a PDF page from text positions (a two-column page read column by column, the banner above first; wide gaps as ` | `; blank lines between blocks) and keeps a Word table row on one line (`htmlToLines`). `cvHeuristics.extractFieldsFromText` returns personal details (name, email, phone, LinkedIn, website, NIN, date of birth, district of origin, place of residence), `education`, `workExperience`, `certificates`, `examGrades` (O/A-Level) and `warnings`: headings from a wide vocabulary (`HEADINGS` - add a heading there), entries read as blocks (labels, table rows, title/employer in either order), dates in the usual forms (`readRange`). Tested against varied layouts in `tests/cvHeuristics.test.js` (`tests/fixtures/cvSamples.js`) and `tests/cvParser.test.js` - add a sample when a CV is misread. Everything read is added at once, with no list to add from one by one (`CvAutofillPanel.jsx`): each entry goes into `ProfileEntriesEditor` (below) unless the profile has it, personal details and LinkedIn fill only what the profile lacks, and a summary says what was added, what was skipped and which entries still need a detail. It's unrelated to the application-level CV upload (an `ApplicationDocument` of category `CV`), which does store the file.

### Auth & RBAC

**Sign-in is Microsoft Entra ID for staff and internal candidates** (`services/entraAuthService.js`; frontend `models/entraAuth.js`, MSAL popup, redirect page `public/entra-redirect.html`). Two app registrations: staff (`ENTRA_STAFF_CLIENT_ID`, may be assignment-restricted in Entra) and candidate (`ENTRA_CANDIDATE_CLIENT_ID`, whole tenant). The browser posts the ID token to `POST /api/staff/auth/entra` or `POST /api/candidates/auth/entra`; the API checks signature (JWKS), audience, tenant, age (10 min), not a guest (`acct`), and an `INTERNAL_EMAIL_DOMAIN` address, then issues our own JWT. **Entra proves identity only - it has no HR classification, so access comes from our rows**: staff sign-in needs an active `StaffUser` for that email (linked to the Entra `oid` on first sign-in, `StaffUser.entraObjectId`, oid-only after that; a mailbox now on a different oid is refused). Internal candidates are exactly the Microsoft sign-ins on the candidate app (first sign-in creates the `Internal` `Candidate`, no password, `Candidate.entraObjectId`); a UCAA address can't register a password account (400 `USE_MICROSOFT`), and every password account is External. An older password account on a UCAA address is linked and switched to Internal at its first Microsoft sign-in only when it has nothing in flight on an External vacancy (else 409 `EXTERNAL_APPLICATIONS_IN_PROGRESS` - they keep the password until those finish). External candidates keep email + password. Staff have no passwords: `POST /api/staff/auth/login` answers 404 unless `BREAK_GLASS_LOGIN=true` (system administrators with a password from `scripts/createSystemAdmin.js --break-glass`) or `DEV_PASSWORD_LOGIN=true` outside production (seeded demo accounts); each use is audited (`PasswordSignIn`). There is no staff forgot/reset password any more. **An ended session ends in the browser too**: a 401 on any request that carried a session token (outside `/auth/` sign-in calls, which use 401 for wrong credentials) fires `SESSION_ENDED_EVENT` in `apiClient.js`; `AuthContext` signs that session out and the sign-in page says why (`useSessionEndedMessage`: deactivated, or expired) - so deactivating a staff member also takes them out of any open page at once.

**One person, two accounts**: a UCAA employee can have a `StaffUser` and an Internal `Candidate`, matched by `entraObjectId` or email; the session type (`staff`/`candidate`) comes from where they signed in. **Conflict of interest** (`services/conflictOfInterestService.js`, `middleware/applicantConflict.js`): a staff member with any non-Draft application on a vacancy (withdrawn included) - or whose delegator has one, while acting under the delegation - gets 409 `APPLICANT_CONFLICT` from every staff route on that vacancy (`guardVacancy(vacancyFrom.param|application|offer|interview|panelMember|candidate|auditEntity)` after `requireStaffRole`), `GET /api/vacancies/:id` included, and that vacancy is left out of the cross-vacancy lists (applications queue/count, admin vacancies, interviews list/attention, offers lists, pending merit lists, upcoming interviews). Their work on every other vacancy is unaffected. Notices addressed to a vacancy's creator or to whoever scheduled an interview (new application, deadline passed, results overdue, reschedule request) pass through `conflictOfInterest.noticeRecipients(vacancyId, staffIds)`: an applicant is left out, and if that leaves nobody the Principal_HR_Officers who didn't apply get it instead (Managers if none) - use it for any new notice aimed at particular staff about a vacancy. Submitting an application as a staff member notifies the other Principal_HR_Officers (Managers if none), `StaffApplicantConflict`. **Add the guard to any new staff route that works on a vacancy or its applicants.** People named on a vacancy without an account are checked too (`conflictOfInterest.applicantAmong(vacancyId, [{ name, email, staffUserId? }])`): an interview panelist who applied is refused (422 `PANELIST_IS_APPLICANT`, on schedule/sessions/add/email change), as is a hiring manager (422 `HIRING_MANAGER_IS_APPLICANT` on the vacancy edit) and a committee member who applied after being nominated (422 `MEMBER_IS_APPLICANT` when rating opens); a hiring manager who applies later gets no more updates (`hiringManagers.notify` leaves an applicant out) and the Principal_HR_Officers are told (`flagHiringManagerApplicant`).

**System administrator** (`StaffUser.isSystemAdmin`, `requireSystemAdmin()`): manages staff accounts (`/api/staff-users` writes: create any role, change role/department/admin/active, unlink the Microsoft id; `StaffAccounts.jsx` at `/hr/staff-accounts`) and nothing else - it sits outside `ROLE_RANK`, and an accounts-only admin has `role` null, so no HR gate passes and `fileController` refuses them. An account's `department` is `HR` or `ICT` (`utils/staffDepartments.js`, mirrored in the frontend; validated on create/update, a select on Staff accounts; the staff session carries it, `AuthContext` `staff.department`). **HR Manager** (`staffUserController.hrTeam`/`updateHrTeamRole`, `GET /api/staff-users/hr-team`, `PATCH /api/staff-users/hr-team/:id/role`; `views/HrTeam.jsx` at `/hr/team`, Setup > HR team): a Manager or Director by their **own** role (re-read; a delegation isn't enough) in the HR department sees only the HR department's accounts and changes their HR roles - only for staff ranked below them, only to a role below their own (never none), never their own account or a system administrator's; someone outside HR answers 404. They can't create, deactivate, move departments, grant admin or unlink - that stays with system administrators. Audited `HR role changed by HR Manager`. Otherwise no HR role manages accounts. Nobody edits their own account; the last active admin can't be removed. Creating an account: "Full name" searches the UCAA directory (`DirectoryPersonField`; `GET /api/directory/people` is open to system administrators too) and a pick sends `entraObjectId`, so the account is linked from the start; "Waiting for a role" lists people assigned to the staff app in Entra, directly or as a direct member of an assigned group (Entra ignores nested groups for app access), with no account yet (`GET /api/staff-users/entra-assignments`, `directoryService.staffAppAssignments`; Graph application permissions `Application.Read.All` + `GroupMember.Read.All`, see SETUP.md) - the admin only picks the role. Entra assignment alone grants nothing. **The staff app's Entra group** (`services/staffGroupService.js`, set up only when `ENTRA_STAFF_GROUP_ID` and the directory connection are set): creating an account adds the person to the group assigned to the staff app (`directoryService.addGroupMember`), deactivating removes them, reactivating adds them back, so they can open the app at once. Create then requires a directory pick (400 `PICK_FROM_DIRECTORY`). It never undoes the account change: the outcome is kept on `StaffUser.entraGroupState` (`InGroup`/`NotInGroup`/`Failed`) + `entraGroupError` (plain words, never Graph's text), audited, shown as "Staff app access" with **Retry** (`POST /api/staff-users/:id/entra-group`), and a failure tells every active system administrator once (`StaffGroupSyncFailed`, email + in-app; their bell and `/api/notifications` are open to system administrators without an HR role). The sign-in email goes once they are in the group. The app holds no group-writing Graph permission - an Entra administrator gives it a custom role scoped to an administrative unit holding only that group ([docs/entra-staff-group-setup.md](docs/entra-staff-group-setup.md)); `scripts/syncStaffGroup.js` (lists, `--yes` applies) brings accounts from before into line. `requireStaffRole`/`requireSystemAdmin` re-read the account each request (`staffModel.findAuthState`), so deactivation (`StaffUser.active`) and role changes apply at once, not at token expiry; inactive staff also get no notifications and lose delegated authority. `requireCandidate` does the same (`candidateModel.findAuthState`): an erased candidate (`purgedAt`) gets 401 "This account has been closed", and `req.user.candidateType` is refreshed from the row. A candidate session carries `tv` = `Candidate.tokenVersion`, which a password reset increments, so every earlier session gets 401 (`loadCurrentCandidate`, also used by the file route). Candidate login answers an unknown address like a wrong password (a bcrypt comparison either way), says "confirm your email" only after the password matched, and tells any UCAA address with no password account to use Microsoft; forgot-password doesn't wait for the email. Emailed links are consumed conditionally (`usedAt: null`), so two racing requests can't both use one.

Two independent JWT session types, both verified by the same `authenticate` middleware (`backend/src/middleware/auth.js`), distinguished by `req.user.type`: `'candidate'` and `'staff'`. `requireCandidate` gates candidate-only routes; `requireStaffRole(minRole)` gates staff routes by a **cumulative 5-tier role hierarchy**: `HR_Officer < Senior_HR_Officer < Principal_HR_Officer < Manager < Director` (`ROLE_RANK` in `auth.js` — the README's "3-tier" description predates this and is stale, trust the code).

**Delegation**: a staff member can be granted another's role rank for a bounded time window (`Delegation` model). `requireStaffRole` checks for an active delegation only when the requester's own rank fails the gate (avoids a DB query on every request), and if one is used, logs the specific action to `DelegationUsage` — the audit trail shows exactly when a delegation was actually exercised, not merely when it was active. This is distinct from and coexists with an older, simpler `StaffUser.actingAsId` static field; don't conflate the two. **An approval given under a delegation counts as the delegator's**: every self-approval check also refuses the delegator's own work (`workflow.actingIds(req)` = the staff member plus `req.actingAsDelegateFor`; vacancy, shortlist, merit list, offer, organisation items and imports, committee nomination), and the Inbox leaves those items out. A delegate whose own role passes the gate acts in their own right and is not affected.

`optionalAuthenticate` fails open to anonymous on a missing/invalid token — used for public browsing endpoints (e.g. job listings) that behave differently for logged-in candidates without requiring login.

### File access

CVs, cover letters, and recommendation letters are served through the authenticated `/api/files/:filename` route (`fileController.js`), never a public `express.static` mount. Staff can view any file; a candidate can only view files attached to their own applications. **Every uploaded document opens in the in-app viewer on click** (`components/DocumentLink.jsx` + `DocumentPreview.jsx`, `audience` staff/candidate/committee): PDFs in the browser's viewer, images as they are, a .docx as HTML from `GET /api/files/:filename/preview` (`utils/documentPreview.js`: mammoth, sanitised, shown in a `sandbox` frame; header auth only, no `?token=`; the committee has `/api/shortlist-panel/:token/files/:filename/preview`), an old .doc as a download only. It is downloaded only from the viewer's Download button (`?download=1&name=`, saved under that name with the stored extension). Use `DocumentLink` for any new document link - never a bare `<a href>` to a file. **CVs**: wherever an applicant's details are shown (applicant card and board, the queue, the candidate search panel, the committee's page, the candidate's own Review step) both their uploaded CV (`DocumentLink`, `uploadedCv(documents)`) and the CV generated from their profile and application (`components/GeneratedCvLink.jsx`: `GeneratedCvPrintLayout` in the same viewer, Download saves a PDF) are offered. Since plain `<a href>` downloads can't set an Authorization header, this route also accepts the JWT as a `?token=` query param, scoped only to file downloads — don't extend that query-param acceptance to other routes. **Uploads never render as pages**: `upload.js` names a stored file by its allow-listed MIME type (`EXTENSION_FOR_MIME`), never the uploader's file name, and `sendUploadedFile` shows only PDF/JPG/PNG/WEBP in the browser (with `nosniff`) and sends everything else as a download - the API shares the app's origin on UAT, where staff tokens sit in `localStorage`. When a change drops the last reference to an upload (a replaced cover letter or score sheet, a removed document, a cancelled draft, a refused upload), delete the file with `utils/uploadFiles.js` `removeUploads` after the change is saved.

**Security headers**: the API sends `helmet`'s headers (`app.js`) with a CSP of `default-src 'none'; frame-ancestors 'self' <FRONTEND_URL origins>` - the app's sites may frame it, since the viewer shows PDFs from `/api/files` in a frame; `sendUploadedFile` gives an inline file `frame-ancestors` only, so a browser's PDF viewer isn't held back. The built site gets its CSP, `X-Frame-Options`, HSTS (with TLS) and the rest from the `security-headers` plugin in `frontend/vite.config.js` (`vite preview` only; the dev server is left alone): scripts from `'self'` only, connections to the API (`VITE_API_URL`) and Microsoft (login, Graph). **No inline scripts or `on*=` attributes** in anything the app renders or writes into a window - wire handlers from code (as `printDocument` does). A new outside service needs adding to that CSP. The API listens on `HOST` when set (`127.0.0.1` on UAT, behind the preview proxy), and in production refuses to start with a `JWT_SECRET` under 32 characters.

### Org structure model

`Directorate → Department → Position → Vacancy`, each level created/approved by staff and carrying its own `createdById`/`approvedById` audit trail. **A department can sit outside every directorate** (`Department.directorateId` null - the Director General's Office): chosen as "No directorate" on the Departments page, a blank directorate code and name in an import row; such departments' codes and names are unique among themselves, checked in code (MySQL doesn't enforce a unique key holding NULL); they have no directorate head, so their staff report to someone more senior in the department. **Each has a short `code` and a full `name`**, both required when added or imported (`utils/orgFields.js`, mirrored in the frontend: upper-cased, letters/digits/spaces/`& / . -`, at most 20): directorate codes are unique, department codes unique per directorate, position codes per department. `name` is the full name - directorates and departments used to be stored by their short names, which migration `20261025090000_org_codes` moved into `code` (spelling out the ones we knew); `Position.code` is null on positions from before until HR gives one (an edit requires it). Staff screens show directorates by code and departments/positions by name; the requisition matcher and the staff-account department lookup accept either. **Managing** (`services/orgAdminService.js`): `GET /api/directorates`, `/api/departments/admin`, `/api/positions/admin` (HR Officer+) list every row in any status with its counts (departments/positions; positions/vacancies/staff; vacancies); `PATCH` and `DELETE /api/{directorates|departments|positions}/:id` edit (code, name, director details; a department's directorate; a position's level - never its department) and delete - by a PHRO+ (own role or delegation, logged), or by whoever added it while it is still `Pending` (deleting their own is audited `Withdrawn`); a rejected item can't be edited; delete answers 409 `ORG_IN_USE` while anything uses it; audited `Edited`/`Deleted`. Frontend: `views/organisation/` - `OrgOverview` (`/hr/organisation`: figures, waiting for approval, import, recent changes) and one page per level (`/hr/organisation/directorates|departments|positions`, table + side panel with history and actions, `?open=<id>`, `?add=1`), under the sidebar's Organisation group (`Sidebar` items with `children`); `/hr/departments` redirects. **Directorates, departments and positions share one approval rule** (`services/orgApprovalService.js`; `status` `Pending`/`Approved`/`Rejected` - the `DepartmentStatus` enum - distinct from `Vacancy.status`): a Principal_HR_Officer+ (own role or delegation) approves what they add at once - the "Approve now" box on each Add form and the import, ticked by default (`autoApprove`; only an explicit `false` sends it for approval); anything else (every HR/Senior HR Officer department or position, or PHRO+ with the box unticked) arrives `Pending` for a PHRO+ who did not add it (`PATCH /api/{directorates|departments|positions}/:id/approve|reject`, 403 `SELF_APPROVAL` for the creator, conditional on still `Pending`). Only a position that is `Approved` in an `Approved` department under an `Approved` directorate (or none) is usable (`positionModel` lists, `orgApproval.usablePosition` in vacancy create); rows from before default to `Approved`. Every creation (`Created and approved (Approve now)` / `Created, sent for approval`), approval and rejection is audited (entity types `Directorate`/`Department`/`Position`/`OrgImport`, `payload.autoApproved`), shown on the Organisation page's "Recent changes" (`GET /api/audit/organisation`); pending items reach the Inbox (one item per import). `Position.level` is an integer meaningful only *within* the same department (not a global ladder) - entered and shown as words, Assistant 1 / Assistant Officer 2 / Officer 3 / Senior Officer 4 / Principal 5 / Chief 6 / Manager 7 / Director 8 (migration `20261031090000_eight_position_levels` renumbered the earlier five; not every directorate uses every level; job grades, unrelated to the HR roles in `ROLE_RANK`; "Senior" is still read as Senior Officer) (`utils/positionLevels.js`, mirrored in the frontend; the API accepts the word or the number). **Reporting lines** (`services/reportingLineService.js`, the vacancy's "Reports to"): every Director (and the DDG) reports to the Director General (the approved Director-level position named "Director General" or coded `DG`); every Manager reports to the head of their directorate, and everyone in the head's own office reports to the head directly; otherwise someone more senior in the same department. The head is `Directorate.headPositionId` (its Director; for Corporate the Deputy Director General, in the DDG's Office), set in the directorate's Edit form; until set, the directorate's one approved Director-level position stands in if there is exactly one (Corporate has the DG and DDG, so it must be set). Only those are offered - more senior positions in the job's **own department**, the directorate head, and the DG for a Director; never a position in another department of the directorate (strictly more senior: a post at the same level can't be chosen, so nothing can report to an Officer-level post): `GET /api/positions/:id/senior-options` returns each option with `directorateHead`, `directorGeneral`, `outsideDepartment` and marks the one the rules point to `suggested` (the form pre-selects it); vacancy create accepts exactly those options; the requisition matcher matches the document's "Reports to" among them (warning, with where it is, when it is outside them) and uses the suggestion only when the document names no one. And a position name is unique per-department, not org-wide, because the same title/department name (e.g. "CWG") legitimately recurs under different directorates — see the `@@unique([name, directorateId])` / `@@unique([name, departmentId])` composite keys in `schema.prisma` before assuming a plain unique constraint. **Batch import** (`services/orgImportService.js`, `orgImportController.js`, `OrgImportCard.jsx` on Organisation and Positions; HR Officer+): an .xlsx or CSV, one row per position (`Directorate code, Directorate name, Department code, Department name, Position code, Position, Level`; older files' plain `Directorate`/`Department` columns are read as codes; template from `GET /api/org-import/template`). Directorates and departments are matched by code, positions by title within their department; full names (and a new position's code) are required only for what is new, once per item; a name clashing with an existing item under another code is an error. `POST /api/org-import/preview` checks every row and changes nothing; `POST /api/org-import` re-reads the file and imports it whole or not at all (422 `IMPORT_HAS_ERRORS` with the rows). It never changes what exists - existing rows are skipped; an existing position at another level, or a name/code in the file that differs from what is stored, is a warning. New directorates need Principal_HR_Officer+ (own role or an active delegation, logged). What the import creates follows the approval rule above: approved at once for a PHRO+ with "Approve now" (`OrgImport.autoApproved`), else every new directorate, department and position arrives `Pending` with `importId` (`OrgImport` records each import), and `PATCH /api/departments/imports/:importId/approve` (Principal_HR_Officer+, not the importer) approves all three kinds still pending together, with the same SLA/dashboard follow-through as one by one.

### Vacancy → Application → Offer lifecycle

- A `Vacancy` is `Internal` or `External` posting type only (never both — `Open` was removed; see the enum comment in `schema.prisma` and `applicationEligibility.js` for the matching bidirectional account/vacancy check). Posting type can transition later, gated at Manager/Director tier and audited via `AuditLog` plus a role/previous-value snapshot on the `Vacancy` row itself. The plain edit (`PATCH /api/vacancies/:id`, HR Officer+) changes it only while `PendingApproval`/`Returned`; after approval a different value answers 409 `USE_POSTING_TYPE_TRANSITION`.
- **Deadlines are a day and a closing time in APP_TIMEZONE, 5:00pm unless HR changes it** (as UCAA adverts say, "not later than 5:00pm"): the forms have Deadline + Closing time and send `YYYY-MM-DDTHH:mm` with no zone (frontend `utils/deadline.js`: `deadlineValue`, `deadlineFields` fills the fields from a stored deadline in that zone, `formatDeadline`); `vacancyValidation.parseDeadline` reads that as Kampala time, and a plain `YYYY-MM-DD` as that day at `DEFAULT_DEADLINE_TIME` (17:00, 14:00Z) - never `new Date(day)`, which is UTC midnight. A timestamp with a zone is kept as sent. Deadlines from before are 23:59:59.999, shown as 23:59; "deadline moved" (edit reason, posting-type transition) is compared to the minute so re-saving an untouched form is no change. Show deadlines with their time (`formatDeadline`, backend `interviewFormat.formatDeadline`); the adverts' "not later than ..." wording uses the vacancy's own time. The requisition reader keeps the document's closing time (`parseDeadlineText`: "5:00pm, 29TH May 2026" -> `2026-05-29T17:00`) and the prefill splits it into `deadline` + `deadlineTime`.
- **Vacancies are created only from an uploaded, EXCO-approved requisition** (no requisition entity or workflow in this system - EXCO approves outside it). `POST /api/vacancies/requisition` (HR Officer+, `uploadRequisition`, PDF/.docx only, stored as `requisition-<uuid>`) reads it: `utils/documentText.js` extracts the text and refuses scans (422 `SCANNED_DOCUMENT` - no OCR), `utils/requisitionParser.js` reads the labelled facts and headed sections of the UCAA template with a confidence per field (`high`/`medium`/`low`, plus `missing` and `warnings`), and `services/requisitionService.js` matches department/job title/reports-to to the organogram and returns a `prefill` for the form. Screening is **suggested** from the Essential Requirements for HR to confirm (`utils/screeningSuggestions.js`, shown as `screening` in the read result): the education level becomes `minimumEducationLevel` (a choice of qualifications takes its lowest; several requirements, the highest), stand-alone years of experience `minimumExperienceYears`, and the field - which a computer can't match reliably ("or equivalent") - a Disqualifying question in the requirement's own words with the certificate as evidence (none when the requirement offers alternatives) plus `preferredFieldOfStudy` (a flag to HR, never a refusal). Approving a vacancy whose advert lists requirements but checks nothing (`screensApplicants`) answers 422 `NO_SCREENING_CRITERIA` until the approver sends `acknowledgeNoScreening: true` (first approval only; `utils/approveVacancy.js` asks). Alongside it HR uploads the **signed copy** - the scan of the requisition as EXCO signed it (`POST /api/vacancies/requisition/signed-copy`, `uploadSignedRequisition`, PDF/JPG/PNG, stored as `requisition-signed-<uuid>`, never read): the readable document carries the text, the scan the signatures. `create()` needs `requisitionDocument` + `requisitionSignedCopy` (400 `SIGNED_COPY_REQUIRED`) + `requisitionConfirmed: true` and re-reads the stored file itself (`forCreate`), keeping `requisitionDocumentUrl/Name/Hash`, `requisitionSignedCopyUrl/Name` (its SHA-256 in `requisitionDetails.signedCopy`), `requisitionDetails` (what was read, plus `editedFields` - what HR changed from it) on the Vacancy; vacancies from before have no signed copy. One document opens one vacancy (`requisitionDocumentHash` is unique, 409 `DUPLICATE_REQUISITION`); a readvertisement carries the requisition and its signed copy over without the hash. **Job advertisement layout** (UCAA's internal/external advert used as the requisition): the parser also reads the JD table of principal accountabilities as `groups` (`[{ heading, items }]` - numbered titles with their bulleted specific activities in a PDF, Word's symbol-font bullets coming through as U+F0D8; titles told by shape in Word), which the prefill writes into the advert as a numbered list; stops sections at "How to apply" and the closing part (contacts, closing date, signature block); and reads the directorate from "... in the Corporate Division", Internal/External from the heading or job reference, and the closing date (`deadline`, prefilled only while still ahead). An advert names no department, so `matchOrganogram` finds it from the job title among the directorate's positions (`departmentFromTitle`, medium confidence, warned). The requisition's "Desirable" items go to `Vacancy.desirableQualifications` (advert text), distinct from `desirableRequirements` (Qualifying questions). All requisition columns are staff-only (`toPublicVacancy`). `pdf-parse`'s pdf.js misreads Buffers from Node's shared pool - always pass `documentText.standaloneBytes(buffer)`. Tests and seeders build requisitions with `scripts/lib/requisitionDocument.js` (and `scripts/lib/demoVacancy.js` / e2e `createVacancyFromRequisition`). **Job description status** (FR-ATS-018): `requisitionService.jdApproval` reads the requisition's JD status as `approved`/`notApproved`/`unknown` (unknown is not refused). On `notApproved`, `create()` answers 422 `JD_NOT_APPROVED` unless `jdExceptionReason` (10+ characters) is sent, stored in `requisitionDetails.jdException`; `approve` then answers 422 `JD_EXCEPTION_NOT_AUTHORISED` until the approver sends `authoriseJdException: true` (frontend `utils/approveVacancy.js` asks first), which records who authorised it. A readvertisement needs it authorised again. A vacancy has at most 5 screening questions, Qualifying and Disqualifying together (`MAX_SCREENING_QUESTIONS`, `vacancyValidation.screeningQuestionCountError`, mirrored in `ScreeningQuestionsEditor`); an older vacancy above the cap can be edited but not given more.
- **Hiring manager** (`Vacancy.hiringManagerName/Email/EntraId/JobTitle`, staff-only, `services/hiringManagerService.js`): the UCAA employee a vacancy is filled for, chosen on New Listing or the vacancy page (`HiringManagerPicker.jsx`; `hiringManager` on create/update/readvertise, an `INTERNAL_EMAIL_DOMAIN` address, `null` clears; readvertising carries it over). Picked from the Entra directory - in the browser with the HR user's delegated Graph permission (`models/entraAuth.js` `searchStaffDirectory`, User.Read.All then User.ReadBasic.All), else `GET /api/directory/people` (`directoryService.js`, app permission + `ENTRA_DIRECTORY_CLIENT_SECRET`; 501 `DIRECTORY_NOT_CONFIGURED` without), else typed in. No system access: `hiringManagers.notify(vacancy, event, details)` emails them (never throws) when the vacancy is approved (`published`), rejected/closed, its deadline passes (`applicationsClosed`, from `checkVacancyDeadlines`), EXCO's shortlist approval is attached, interviews are booked, the merit list is approved, and an offer is accepted or not taken up (declined, withdrawn after issue, expired); also as the vacancy moves on - review begins (`reviewStarted`, Begin Review), the committee starts rating (`shortlistingStarted`) and closes (`shortlistingComplete`), an offer is issued (`offerMade`). Never per application: `applicationsClosed` gives the count only, no summary of the applicants.
- **Vacancy drafts** (`VacancyDraft`, `vacancyDraftController.js`, `/api/vacancy-drafts`, HR Officer+, private to their writer): the New Listing form plus the requisition read result and the signed copy (`signedCopy`/`signedCopyFilename`), saved with "Save draft" and auto-saved ~2s after changes once a requisition is read (`models/useVacancyDraft.js`); reopened via `/hr/vacancies/new?draft=<id>` from the Vacancies page (`VacancyDraftsList.jsx`). Not a `Vacancy` row - no job reference, never listed. Saves send `baseUpdatedAt` and answer 409 `DRAFT_CHANGED` if another window saved since, rather than overwriting. The EXCO confirmation is never saved; `create()` with `draftId` deletes the draft.
- **Job references** are `UCAA/ADV/{INT|EXT}/{NNN}/{YYYY}` (`utils/jobRefGenerator.js`): a running number per posting type per year (APP_TIMEZONE), taken from the `JobRefSequence` row under its lock inside the transaction that creates the vacancy (`vacancyModel.createWithJobRef`), so numbers are never reused or skipped. Refs made before this (`UCAA/ADV/EXT/09/2026[-n]`) are left as they were.
- **Vacancy approval answers**: approve (`Open`), `PATCH /:id/return` (`Returned`, comment in `returnReason`; HR edits and `PATCH /:id/resubmit`s it, which sets `approvalRequestedAt` and restarts the SLA clock) or `PATCH /:id/reject` (`Rejected`, final, `rejectionReason`); return/reject are Manager+ and need a comment, and the creator is notified (`VacancyReturned`/`VacancyRejected`). Closing (the "unpublish") needs a reason (`closeReason`) and, for a vacancy that was published, **evidence it was advertised** (`VacancyAdvertEvidence`: multipart `evidence`, 1-5 PDF/image files stored `advert-evidence-<uuid>`, optional `evidenceNote`; 400 `ADVERT_EVIDENCE_REQUIRED` unless some is already on file; kept only if the vacancy closes; more added at `POST /:id/advert-evidence`, Senior_HR_Officer+; shown on the vacancy page, `components/workspace/AdvertEvidence.jsx`); so does moving the deadline of a published vacancy (compared by calendar day). **Closing with people still in it** (`services/vacancyClosureService.js`; active applications, open or accepted-not-hired offers): `PATCH /:id/close` answers 409 `VACANCY_HAS_WORK_IN_PROGRESS` with `inProgress` counts until `inFlight` is sent - `'continue'` only takes the advert down (selection goes on, as before), `'end'` stops the recruitment in one transaction (vacancy row locked first): open offers `Withdrawn` with nobody promoted, active applications `Rejected` with `DISCONTINUED_REASON` and `statusBeforeRejection`, then booked interviews cancelled and each candidate told `RecruitmentDiscontinued` (not `ApplicationRejected`); refused while an accepted offer is not yet hired (409 `ACCEPTED_OFFERS_OUTSTANDING`). Re-opening brings nobody back - a PHRO reinstates applications. **A deadline can't be moved back into the future once the shortlisting committee is past `Setup`** (409 `COMMITTEE_ASSESSING`, in the edit and the posting-type transition): its applicants are assigned once, when rating opens. Approve/return/reject/close write through `vacancyModel.updateIfStatus`, so two approvers can't both act (409).
- `Vacancy.title`, `Application`'s qualification snapshots, and `Vacancy.approvedByRole`/`postingTypeChangedByRole` are all deliberately denormalized snapshots of what was true at the time an action occurred (not live joins) — if you're tempted to "clean up" one of these into a read-through relation, don't; it's an intentional audit-trail pattern used consistently across this schema.
- **Selection is three steps, each with its own propose/approve split**, worked on the vacancy's own page (`views/VacancyWorkspace.jsx`, tabs Committee / Interviews & EXCO / Merit list & offers): (1) the **interview shortlist** (`ShortlistPipelineBoard`) decides only *who is interviewed, in what order* - it no longer assigns `Primary`/`Reserve` (`listStatus` is written `null`); (2) **interviews** (`VacancyInterviewsPanel`, the Interview Hub); (3) the post-interview **merit list** (`meritListService.js`, `meritListController.js`, `MeritListBoard.jsx`; `Application.meritRank`/`meritListStatus`/`meritStatus`), which ranks `Interviewed` candidates whose latest held round has recorded results with a `Shortlist` or `Hold` verdict. The first `positionsRequired` `Shortlist` candidates are `Primary`, everyone else `Reserve`; a `Hold` may never be Primary nor sit above a `Shortlist`. Proposed by Senior_HR_Officer+ (notifies Principal_HR_Officers, `MeritListProposed`), approved by Principal_HR_Officer+ who proposed none of it; re-proposing needs fresh approval; the list locks (409) once any offer on the vacancy is `Recommended`/`Approved`/`Extended`/`Accepted`. A candidate on the merit list can't be scheduled another round, and a rejection clears their merit entry.
- **Shortlisting committee** (`ShortlistExercise`/`ShortlistMember`/`ShortlistAssignment`/`ShortlistRating`/`ShortlistDecision`; rules in `shortlistCommitteeService.js`, HR side `shortlistCommitteeController.js` + `ShortlistCommittee.jsx` at `/api/shortlist-committee/vacancies/:vacancyId`, members' side `shortlistPanelController.js` + `ShortlistPanelAccess.jsx` at the public `/api/shortlist-panel/:token` and `/shortlist-panel/:token`). Stages `Setup -> Rating -> Moderation -> Closed`. HR (Senior_HR_Officer+) builds the assessment sheet (generated from the vacancy's person specification via `defaultCriteria`, editable, frozen when rating opens) and invites the committee: anyone at UCAA, HR included (an `INTERNAL_EMAIL_DOMAIN` address); someone from outside only as a rare special case with a reason (`ShortlistMember.externalReason`, 422 `EXTERNAL_REASON_REQUIRED` without one, audited); never an applicant for the vacancy; at least 3, one chair (changeable until close). **The DHRA approves the committee** (FR-ATS-046, `ShortlistExercise.nominationStatus` `Draft -> Submitted -> Approved | Returned`): HR `POST .../nomination/submit`s it (Directors notified, `CommitteeNominationSubmitted`); while `Submitted` only a Director (own role or delegation) can change the members, each change audited as `DHRA ...`; a Director other than the submitter `nomination/approve`s it or `nomination/return`s it with a reason (10+ characters; the submitter is told, `CommitteeNominationDecided`); Directors get it in their Inbox and review it there (`GET /api/shortlist-committee/nominations/pending`). `open` answers 422 `NOMINATION_NOT_APPROVED` until approved, and an HR change to the members after approval puts it back to `Draft`. Members' links stop working at `accessExpiresAt` (optional, FR-ATS-048) as well as at close. Rating opens only after the application deadline; every `UnderReview` applicant is assigned (`planAssignments`: a calibration set of `calibrationCount` drawn at random that everyone rates - recorded in the "rating opened" audit as `calibrationSet` - then sub-panels of `ratersPerApplicant` with balanced load). Members rate through their private link (its list searched by name, filtered by To rate / Rated / Stood down / Calibration, and paged; prev/next and "Save and next" walk the list as filtered when the applicant was opened), blind to each other - essential criteria Met(2)/Partly(1)/Not met(0, needs a comment), desirable 1-5 - editable until they submit; they can stand down per applicant, and see that applicant's documents only through the link (`/files/:filename`, checked against their assignments). Only submitted, non-conflicted ratings count, and an applicant with fewer than two of them (`MIN_RATERS`) has every essential criterion go to the chair; during rating GET's `coverage` lists such applicants and HR adds a rater (`/assignments`, emailed; only members who haven't submitted). `computeResults` bands each applicant (Unanimous > Majority > Disputed > NotQualified, by majority of "Met"/"Not met" votes per essential criterion; anything else is Disputed) and ranks by band, weighted consensus score, agreement, then experience; ties share a rank. At moderation the chair rules on disputed items (`ShortlistDecision`, reason required); for an applicant the chair stood down from, HR names an acting chair (`ShortlistExercise.actingChairs`, `PUT /acting-chairs`, never the chair or anyone who stood down from that applicant, emailed) who rules on that applicant in the chair's place; the exercise can't close while any remain. Closing snapshots `committeeRank`/`committeeBand`/`committeeScore`/`committeeAgreement` on each application (stripped from the candidate's own view). HR then proposes N for interview (`/propose`): strictly the top N qualified plus anyone tied at the cut line, at least `positionsRequired` - it lands at `ShortlistProposed` for Principal_HR_Officer approval as before. **EXCO approves the interview shortlist outside the system** (`excoShortlistController.js`, `ExcoShortlistPanel.jsx` on the Interviews step): after the Principal_HR_Officer approval HR prints the shortlist (`GET /api/vacancies/:id/exco-shortlist`, HR Officer+, and `utils/printDocument.js`), EXCO signs it, and a Senior_HR_Officer+ attaches the signed copy (`POST` same path, multipart `document` + optional `excoReference`/`approvedOn` + `struckOff` = JSON application ids EXCO did not approve). That creates an `ExcoShortlistApproval`, sets `Application.excoApprovalId` on everyone it covers (in one transaction, only if they're still `Shortlisted`, unapproved and never interviewed; else 409) and rejects the struck-off ('Not approved for interview by EXCO.'). **Candidates are told they're shortlisted only then** (`approveShortlist` no longer notifies), the struck-off get `ApplicationRejected`. My applications keeps to the same rule: `candidateController.candidateStatus` shows `ShortlistProposed`, and `Shortlisted` with no `excoApprovalId` and no interview round, as `UnderReview`, and strips the shortlist/EXCO columns and `shortlistScore`. A first interview needs it: `schedule`/`plan`/`sessions` answer 409 `EXCO_APPROVAL_REQUIRED` for an application with no `excoApprovalId` and no interview round yet (later rounds, and rounds booked before this step existed, don't). A later, additional shortlist gets its own approval. **HR cannot reorder**: a vacancy with an exercise refuses `saveRanking` and single `shortlist` (409), and the board hides hand-ranking.
- **One board for every stage** (FR-ATS-042/043; `pipelineColumn` in `components/workspace/pipeline.js`, the Stage column and chips of the vacancy page's Applicants tab, `components/workspace/ApplicantsTable.jsx`): columns Applied -> System shortlist -> Shortlisting by committee -> Approval by EXCO -> Interviews -> Offer -> Onboarding, plus Not progressing, worked out from each application's record (`pipelineColumn`: status, committee stage, `excoApprovalId`, offer, `hire`) - never stored. Dragging (`BoardView` `onMove`/`canDrag`) only does what one audited action does: to Not progressing rejects (`PATCH /api/applications/:id/reject`, reason asked), Offer -> Onboarding opens Mark as Hired; every other move answers with the step that makes it, since each has its own approver. Cards can be selected to email or reject together; the board searches by name, email or tag.
- **Candidate tags and search** (FR-ATS-051/052; `talentController.js`, `/api/talent`, `components/TagEditor.jsx`, `views/CandidateSearch.jsx` at `/hr/candidates`): `CandidateTag`/`CandidateTagging` - HR's labels on the candidate, shown on applicant cards and the board (`candidate.tags` in `applicationModel`'s `CANDIDATE_SELECT`); any HR tier tags, Senior_HR_Officer+ deletes a tag. `GET /api/talent/candidates?q=&tags=&candidateType=&page=` searches everyone who submitted an application (past applicants included; never erased ones, never the searcher's rivals): every word must match the name, email, phone, residence, district, education, employers/job titles or certificates. Results are access-logged (`Searched candidates`) and carry their latest uploaded `cv`; `GET /api/talent/candidates/:candidateId` (same filters, access-logged `Viewed candidate profile`) gives the full profile and latest application for the generated CV. The erasure purge removes a candidate's tags.

### Candidate application flow

Candidate-facing application is a multi-step wizard (`frontend/src/views/careers/CareerApply.jsx`, reusing the steps in `views/apply-wizard/`: `ProfileStep`, `QuestionsStep`, `RefereesStep`, `DocumentsStep`, `ReviewStep`, `SubmitStep`), backed by a real draft/submit/withdraw workflow (`applicationDraftController.js`) rather than local-only wizard state — profile fields (`location`, `linkedinUrl`, etc.) persist on `Candidate` across every application; per-application answers (`whyThisRole`, `desirableResponses`, etc.) persist on `Application` (a desired salary is no longer asked; the column keeps older answers). **Education, work experience and certificates** are edited in place by `components/ProfileEntriesEditor.jsx` (My profile, Internal Careers' welcome, `/profile/complete`): a saved entry is one summary line with Edit (opens its fields; no Done per entry - each saves itself) and Delete (asks first); the Done of the panel or page around it calls the ref's `finish()` (drops blank new entries, saves what is waiting, refuses while an entry someone started lacks a required field); only an entry needing attention opens by itself (new, a required field missing, a failed save); "Add another" only opens a blank one, and an entry saves itself ~0.8s after a change once its required fields are filled (POST, then PUT); O-Level and A-Level results (`ExamGradesEditor`) sit inside the Education section (`educationExtra`). On My profile, Education (with those results), Work experience and Certificates are separate panels, each with its own form: "+ Add" opens only that kind with a blank entry ready (`kinds`, `startNew`), a row's Edit opens that entry (`focus`; a job with its duties), Delete asks first, and each job shows how many duties are on file; Job duties are one text box taking a pasted bulleted or numbered list, split into the stored list by `utils/dutyList.js` `splitDuties` (mirrored in the backend, which also splits a duties string and the CV reader's duties) and shown back one bullet per line; its ref offers `addFromCv` and `flush`. `Vacancy.desirableRequirements` ("Qualifying" questions in the HR editor) are Yes/No or number questions with a stable generated `id` per requirement so an applicant's snapshotted answer stays attributable even if the vacancy wording is later edited; a "No" answer is informational only (a ranking signal, never a block). Answers are snapshotted against the vacancy's questions at every draft save and again at submit (`snapshotDesirable`/`snapshotDisqualifying`), so an application is screened on the questions as they stand when it is submitted.

**Internal candidates apply only once HR has verified their employment** (`utils/employmentCheck.js` - `HR_Verified` with evidence on file; one check per person, `InternalProfile`): `submit()` answers 422 `EMPLOYMENT_NOT_VERIFIED` (with `employmentCheck`) otherwise - drafts are allowed and kept - and `GET /api/applications/eligibility/:vacancyId` returns `employmentCheck` so the job page, jobs table, apply wizard's Check and Submit steps and Internal Careers home say so up front. HR checks from **Employment checks** (`/hr/verification`, `views/EmploymentChecks.jsx`, Recruitment in the sidebar; `GET /api/verification/pending[?include=all]`, HR Officer+; one Inbox item `employment-checks` for Senior HR Officers and Principal HR Officers), deciding through `services/internalVerificationService.js` `decide` (`PATCH /api/verification/candidates/:candidateId/verify`, Senior_HR_Officer+, comments 20+ characters or a manager's letter): audited on `InternalProfile` (shown as its history; `InternalProfile` is in `HISTORY_ENTITY_TYPES`), the candidate told (`EmploymentVerified`/`EmploymentDiscrepancy`), a replaced letter removed, never the viewer's own (403 `SELF_VERIFICATION`; their own profile is left out of the queue). `InternalProfile.detailsUpdatedAt` is when the details were given or last changed (how long the check has waited); a change after a decision puts it back to `Pending`, audited. Applicants from before the rule who are still unverified stay in the pool, are listed in the queue with their applications, and are warned about on the committee step (`unverifiedInternal` in the committee GET) - the shortlist rule (`assertCanShortlist`) still refuses them.

**Screening happens at the point of application**: `submit()` runs `screeningService.assessEligibility` and refuses (422 `NOT_ELIGIBLE` with `reasons`) a candidate who fails any structured minimum on the vacancy (education, experience, age, flying hours, exam grades, CGPA - missing profile data counts as a fail) or answered a `disqualifyingRequirements` question the wrong way (400 while one is unanswered). Only eligible candidates reach the applicant pool, and every submitted application is stored already screened; Begin Review re-screens against the current profile. The wizard surfaces the same check early via `GET /api/applications/eligibility/:vacancyId` (Job Details warning, Submit step) and stops the candidate on the Questions step as soon as a Disqualifying answer fails (`utils/screeningQuestions.js`). Submit also requires explicit consent (`{ consent: true }`, else 400 `CONSENT_REQUIRED`), stored as `consentGivenAt`/`consentNoticeVersion` against the privacy notice at `/privacy` (`frontend/src/data/privacyNotice.js`; bump its version together with `backend/src/config/privacyNotice.js` - the wording is a draft pending UCAA Legal). The Uganda NIN (`Candidate.nationalId`) is the only identity document an External candidate gives (Internal ones give their employee number instead) - no passports, no ID-type choice (`idType` was dropped): it is stored upper-cased (`normalizeNationalId`) and must match `NATIONAL_ID_RE` at registration, on profile save and for profile completeness. `Candidate.districtOfOrigin` is required for a complete profile; `location` is the place of residence. **Evidence** (`utils/screeningEvidence.js`, mirrored in `frontend/src/utils/screeningEvidence.js`): what screening relies on must be backed by an `Evidence` `ApplicationDocument` filed under its `evidenceKey` - `nationalId` for an age limit, `flyingHours`, `examResults`, `experience` (minimum experience), `transcript` (minimum CGPA), and `question:<id>` for a screening question HR marked `evidenceRequired` (with `evidenceLabel`) that the candidate answered Yes or with a number above 0. Upload with `category: 'Evidence'` + `evidenceKey` (refused if the vacancy doesn't ask for it; labelled with the requirement); submit answers 400 `EVIDENCE_REQUIRED` with `missing` after the eligibility check, and `GET /api/applications/eligibility/:vacancyId` returns `evidence` with `provided`. The Documents step collects them. Submit also requires at least one `Academic` `ApplicationDocument` (plus optional `Other` documents and an optional `CV` - the candidate's own, one per application, a new one replacing it; PDF/Word/JPG/PNG, uploaded one at a time via `POST/DELETE /api/applications/:id/documents` while the application is a Draft, served through `/api/files` like cover letters).

### Frontend routing/layout

**Staff workspace** (the agreed design): every staff page is one of a few layouts built from `components/workspace/ui.jsx` (styles in `workspace.css`) - `PageTop` (title, subtitle, actions on the right), `Chips`, `Table`, `Panel`, `Figures`, `SidePanel` (work on one item without leaving the page), `MenuButton`. **Every table pages** (`components/Pagination.jsx`): `Table` and `DataTable` page the rows they're given by default (25 a page, rows-per-page 10/25/50/100 remembered per browser, back to page 1 when the rows change; `pagination={false}` to show all). A list paged on the server passes `pagination={pageProps(total)}` from `useServerPagination()` and sends `page` + `limit`/`pageSize` (applications, offers, talent search, audit log). A hand-built `<table>` uses `usePagination(rows)` + `<Pagination {...pager.props} />`. The sidebar (`HRSidebar`) is My work (Inbox) / Recruitment (Vacancies, Candidates, Interviews, Offers & hires) / Reports (Dashboard, Manager+) / Setup (Organisation, Document templates, Delegations, Settings & data, Staff accounts). **Inbox** (`/hr/inbox`, every role's landing page, `views/Inbox.jsx`; `GET /api/dashboard/inbox`, `services/inboxService.js`) lists what is waiting for the viewer - each vacancy's next step for their tier and the tier above (effective rank includes an active delegation), plus each offer/department approval, data requests and reschedule requests, with SLA due dates; approvals are reviewed in a side panel (`components/workspace/ReviewPanel.jsx`). The sidebar count shares it (`models/useInbox.js`; call `refreshInbox()` after an action). **Vacancy progress** (`services/vacancyProgressService.js`, never stored): stage, the 8-step bar (Approval, Advertised, Committee, EXCO, Interviews, Merit list, Offers, Hired) and the next step with who acts - on each row of `GET /api/vacancies/admin` (`progress`) and at `GET /api/vacancies/:id/progress`. **Vacancies** (`/hr`, `HRDashboard.jsx`) is a table with Stage and Waiting on; a row opens the **vacancy workspace** (`/hr/vacancy/:id?tab=overview|applicants|committee|interviews|merit|history`, `VacancyWorkspace.jsx`): every action in the header (`components/workspace/VacancyActions.jsx`), the Next step box, the step bar, the tabs, and any applicant in a side panel (`ApplicationReviewCard`). Candidates (`/hr/candidates`) has the candidate database and, under Applications, the cross-vacancy queue (`ApplicationQueue.jsx`). Old links redirect: `/hr/home`, `/hr/executive`, `/hr/approvals` to the Inbox; `/hr/analytics*` to `/hr/dashboard`; `/hr/applications?vacancyId=` to the vacancy's tab, without it to Candidates > Applications; `/hr?tab=offers` to `/hr/offers`. The global search in the app bar (`GlobalSearch.jsx`, Ctrl+K) finds vacancies and candidates.

`App.jsx` splits routes into two groups: most routes render inside `PaddedLayout` (adds a padding gutter around `Outlet`); a few self-contained full-bleed pages (`/register`, `/login`, `/apply/:vacancyId`, `/staff/login`) are registered as siblings outside that layout because they manage their own edge-to-edge background and would get an unwanted double inset otherwise. Keep that distinction in mind when adding new routes — decide whether the new view needs the padded shell or manages its own full-bleed layout.

`ProtectedRoute.jsx` exports `RequireCandidate` and `RequireStaff` (the latter taking `minRole`, checked against the same `ROLE_RANK` hierarchy as the backend) — client-side gating only; the backend middleware is the real enforcement.

### Casing of names and titles

`utils/textCase.js` (mirrored in the frontend) is the one rule for how a field is cased when saved: `code` UPPER, `email` lower, `name` (a person) and `title` (a position, department, institution, employer, field of study, qualification) re-cased **only when typed all in capitals or all in lower case** - mixed case is kept exactly ("McDonald", "iOS Developer"); acronyms on its `KEEP` list keep their form in titles ("ICT Officer"), names keep only Roman numerals; capitals with no word longer than three letters ("JMK", "EIC OJT") and vowel-less words in titles ("NWSC") are left alone. `text` (anything someone wrote, advert and requisition wording) is only trimmed, never re-cased. The backend applies it on save with the `casing({ field: kind })` route middleware (candidate profile and registration, staff accounts, directorates/departments/positions, committee members) or `formatAs` where a body is parsed (panelists, hiring manager, referees, the org import); forms show it as a field is left with `<TextField format="name|title">`. Use them for any new name or title field; extend `KEEP` (both copies) when an acronym is missing. `scripts/applyTextCase.js` tidies stored records the same way (lists the changes, applies only with `--yes`).

### Theming

Tailwind is present but **`preflight` is disabled** (`tailwind.config.js`) — older pages were built against plain browser defaults plus `theme.css`, so only Tailwind's utility classes apply (used mainly in newer markup like the apply wizard). Don't re-enable preflight; it would restyle every page. Tailwind directives are imported at the top of `theme.css`.

All brand tokens (colors, spacing, radius, font) live in `frontend/src/theme.css` as CSS variables. Every reusable component reads from these variables rather than hardcoding values, and every view uses these components instead of one-off inline styles or browser dialogs (use themed `Modal`, never `window.prompt`/`window.confirm`). `StatusBadge` centralizes color-per-status-enum (vacancy/application/offer/verification status) in one lookup table — add new status colors there, not per-view (its labels come from `statusLabel`, which turns `PendingApproval` into "Pending approval"). To rebrand: edit `theme.css` variables only.

**Staff workspace look**: `App.jsx` puts `.staff-ui` on `<html>` whenever a staff member is signed in or the page is on the staff port, and `theme.css` redefines the same tokens under it (grey canvas, navy app bar, neutral borders, 6px/4px corners, no footer or breadcrumb strip, soft status pills, accent edges on `Card` only for danger). The candidate site is untouched by it. `HRSidebar` uses `Sidebar`'s `variant="rail"`: fixed flush left under the app bar, with an in-flow spacer so views keep their `flex` row with `<HRSidebar />` first; on phones it opens from the Navbar's menu button (`OPEN_SIDEBAR_EVENT`). Give a staff page's title `PageHeader` (or `className="page-title"`) so every page header looks the same.

### SLA / notifications

`SlaPolicy` (per `taskType` + role `tier`, duration in hours) and `TaskEscalation` back an SLA-tracking layer for `VacancyApproval`/`DepartmentApproval`/`DirectorateApproval`/`PositionApproval`/`OfferApproval` (`slaStatusService.SLA_TASK_TYPES`; add a new timed approval there), checked via `scripts/checkSlaEscalations.js`, which notifies once per import and tier for organisation items from one spreadsheet import. `orgApprovalService.decide`/`approveImport` close the escalations of what they decide. `Notification` supports `InApp`/`Email` channels per recipient staff user, surfaced in the UI via `NotificationBell.jsx`. A separate script, `scripts/checkVacancyDeadlines.js`, notifies a vacancy's creator exactly once (via `Vacancy.deadlineNotifiedAt`) when its application deadline passes while still `Open`/`PartiallyFilled` - it reuses the same `Notification`/`notify()` plumbing (hence the `VacancyDeadlinePassed` `SlaTaskType` value) but is not part of the escalation-tier machinery above. Same for `OfferDeclined` and `VacancyFilledWithOpenOffers` (to Principal_HR_Officers, see the offer lifecycle above) and `SystemHealthAlert` (in-app only, to Directors). `applicationDraftController.submit` fires a `NewApplicationSubmitted` notification (same `notify()` plumbing, also not part of the escalation machinery) to the vacancy's creator on every submission, Internal or External. Nobody else is told about a single application - not a supervisor (that notice was removed), not the hiring manager.

**Approval notices** (`services/approvalNotificationService.js`): a new approval request reaches everyone who may approve it, by email and in-app, the moment it is made - the Inbox's audience (`audienceRoles` = `inboxService.inAudience`: the approving tier and the one above; Manager steps to Managers and Directors) plus active delegates of anyone in it, never whoever made it (nor their delegates acting on their authority) and never staff who applied for the vacancy; nobody with an unread notice about the same request is told again. `notifyApprovers(kind, { taskId, message, excludeIds, vacancyId })` for `vacancy` (create, readvertise, resubmit), `offer` (recommend, resubmit after a return), `shortlist` (`shortlistProposed`, all three ways of proposing), `merit`, `committee`, `directorate`/`department`/`position` (`orgApproval.recordCreated` when not auto-approved; one notice per import, `notifyImportPending`). Add a call for any new approval step, and tag its Inbox item with `notice`. `scripts/sendApprovalReminders.js` runs `inboxService.forStaff` for every active staff member: any approval item (`notice`) they were never notified about gets one in-app notice each and one email listing them (so requests pending before notices existed, or picked up through a new delegation, are covered); and on working days from 08:00 APP_TIMEZONE, once a day (guard: that day's `PendingApprovalsDigest`), a reminder of what has waited 20+ hours. **Notification links** (`Notification.link`, `utils/notificationLinks.js` `linkFor`, also worked out at read time for older rows): an approval opens `/hr/inbox?item=<inbox key>&fallback=<page>` - the Inbox opens that item's review panel, or says it is no longer waiting and offers the fallback; other notices open the vacancy tab, interview or organisation item. The bell (`NotificationBell.jsx`) marks a notice read and navigates there; `PATCH /api/notifications/:id/read` is the recipient's own only, `PATCH /api/notifications/read-all`. Emails carry an "Open in e-Recruitment" button to `staffFrontendUrl` + the link, and the message is HTML-escaped there - don't escape it at the call site. Candidate notices open My applications or My profile on their site (`utils/candidateNotificationLinks.js`).

**Candidate-facing notifications** are a separate, parallel system - `CandidateNotification`/`CandidateNotificationType` (not `Notification`/`SlaTaskType` above), dispatched via `candidateNotificationService.notifyCandidate(candidateId, type, message)` and surfaced via `CandidateNotificationBell.jsx`. A distinct model rather than reusing `Notification`, since `Candidate.id` and `StaffUser.id` are independent autoincrement sequences that can collide in value - see the schema comment on `CandidateNotification`. Current types: `ProfileCompleted` (fired once, `profileCompletionService.js`), `ApplicationSubmitted`, `ApplicationShortlisted`, `InterviewScheduled`, `ApplicationRejected`, `OfferReceived` (fired when an offer reaches `Approved`, the point `CandidateOfferPanel` actually lets the candidate accept/decline it - not at `Recommended`, which they can't see), `OfferWithdrawn`, `OfferExpiring`, `OfferExpired` (both from `scripts/expireOffers.js`), `DataRequestRefused`, `ApplicationReinstated`, `RecruitmentDiscontinued`, `InterviewRescheduled`, `InterviewCancelled`, `InterviewReminder` (the last from `scripts/sendInterviewReminders.js`, about a day ahead). Staff-side interview notices reuse `notify()` with `SlaTaskType` `InterviewRescheduleRequested` and `InterviewResultsOverdue` (`InterviewReadyToFinalize`, `InterviewScoresOverdue` and `InterviewSessionNotStarted` are legacy enum values, no longer sent).

**System health**: `SystemHealth` rows (`job:<name>` per maintenance job, `mail` for outgoing email) record the last success/failure. `utils/mailer.js` writes the `mail` row on every send (successes throttled) and `sendMail` still returns `null` rather than throwing; `SMTP_HOST=json` uses nodemailer's jsonTransport for dev/tests; a missing `SMTP_HOST` counts as a failure. `services/systemHealthService.js` turns the rows into staff warnings for `GET /api/dashboard/system-health` (shown by `SystemHealthBanner.jsx` on the Inbox) and alerts Directors in-app at most once a day per key. Error text stays server-side - never send `lastError` to the browser.

**Rate limiting**: `middleware/rateLimit.js` limits candidate/staff login, forgot-password and candidate registration per address and per account, using an emailed link (confirm email, reset password) per address, and the committee's `/api/shortlist-panel/:token` per address and per link (`panelLimiters`) (in-memory, per process). Per-address limits depend on `app.set('trust proxy')`, set from `TRUST_PROXY` (default `loopback`).

## Testing conventions (backend)

Every suite in `backend/tests/` mocks the shared Prisma client via `jest.mock('../src/config/db', () => require('./__mocks__/db'))` — `tests/__mocks__/db.js` is a hand-maintained object of `jest.fn()`s per model/method. **When adding a new Prisma call in application code, add the corresponding mock method to `tests/__mocks__/db.js` first**, or the test will fail with "not a function" rather than a useful assertion failure. Unit tests never touch a real database. `beforeEach(() => jest.clearAllMocks())` is the standard pattern at the top of each suite. Jest's config is `backend/jest.config.js` (unit) and `tests-e2e/jest.config.js`, both spreading `jest.esm.js`, which turns sanitize-html's ES-module-only parser packages into CommonJS for Jest (Node itself `require`s them) - add a package there if another dependency goes ESM-only.

`backend/tests-e2e/` is the exception: the real app against a real MySQL database (`npm run test:e2e`, `DATABASE_URL_TEST`), for what mocks can't show - locking, unique-key races, queries that no longer match the schema. Each test empties the database; use the factories in `tests-e2e/helpers.js`. The default `npm test` ignores this folder.

## Known gaps (intentional, not oversights)

- The migration history can't build a database from scratch (`20260915120000_age_flying_hours_exam_grades` alters a column no earlier migration creates - columns were added directly on the shared DB; see the READMEs in `prisma/migrations/`). The e2e suite uses `prisma db push` instead. New migrations still go in `prisma/migrations/` as usual.
- Rate limits are in-memory per API process; a multi-process deployment would need a shared store.
- The frontend tests cover shared logic, components, routing gates and the API client, not the big pages (the Inbox, the vacancy workspace, the apply wizard) - the committee member's page is the only page tested.
- `docker-compose.yml` exists but isn't wired up for local dev — use the two-terminal `npm run dev` flow (backend + frontend) in [SETUP.md](SETUP.md) instead. The user-testing deployment is `deploy/lan/` (one Windows server, its own worktree/DB/uploads; `vite preview` serves the build over HTTPS on 443 (careers, office address only - Tailscale holds 443 on its own addresses)/4174/4175, port 80 redirects to https; the process list is `deploy/lan/processes.ps1`, re-read on every restart; it proxies `/api`/`/ws` to the API - built with `VITE_API_URL=same-origin`, `PREVIEW_*` settings in `vite.config.js`; `npm run db:prepare` = `scripts/prepareDatabase.js`, `db push` + baseline on an empty DB, else `migrate deploy`).
- An Internal candidate who leaves UCAA loses their Microsoft sign-in and with it their candidate account, pending interviews and offers included - decided, not an oversight; there is no move to a personal email.
- Entra ID is used for sign-in only - no HRMS/Graph sync. `candidateType` Internal means "signed in with a UCAA Microsoft account"; `InternalProfile` fields (employee number, department, job title, date joined) are self-declared + HR-verified, not read from Entra, which holds no department/trade data. Committee members and interview panelists still get link-only access (no Microsoft sign-in yet).
